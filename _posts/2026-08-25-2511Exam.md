**Q10 (4 marks)**
Consider the following classes:

```java
public class Shape {
  /**
   * @preconditions - sideLength > 0
   * @postconditions - returns the perimeter of the shape
   */
  public double perimeter(double sideLength) {
    return 0;
  }
}

public class Square extends Shape {
  /**
   * @preconditions - sideLength >= 0
   * @postconditions - returns the perimeter of the shape, or throws
   *                 InvalidShapeException if sideLength == 0
   */
  @Override
  public double perimeter(double sideLength) throws InvalidShapeException {
    return 0;
  }
}
```

Is this a valid overriding of the contract from `Shape` to `Square`, with respect to Design by Contract? Justify your answer with reference to preconditions, postconditions, and exception rules for overriding.

> ### ✅ Model Answer
> This is **not** a valid override under Design by Contract rules.
>
> 1. **Precondition direction:** `Shape.perimeter` requires `sideLength > 0`, while `Square.perimeter` only requires `sideLength >= 0`. This is a *weakening* of the precondition (0 is now additionally allowed), which **is legal** — subclasses may weaken/relax preconditions, never strengthen them. So this part alone is fine.
> 2. **The actual problem is the postcondition/exception.** `Square.perimeter` introduces a brand new checked exception (`InvalidShapeException`) and a new failure behaviour (throwing when `sideLength == 0`) that is not part of the contract inherited from `Shape`. Overriding may only **strengthen** postconditions (guarantee *more* than the parent, never less, and never introduce new ways for the client to be surprised). Since a client coded against `Shape.perimeter()` would never expect an exception, this override breaks the Liskov Substitution Principle: substituting a `Square` for a `Shape` can now cause client code to crash in a way it previously could not.
> 3. **Compilation note:** this would also fail to compile as written in Java — a subclass's `throws` clause may only be a subset of the superclass method's `throws` clause, and `Shape.perimeter()` declares no checked exceptions at all, so `Square.perimeter()` cannot legally add one.
>
> **Conclusion:** invalid override — the exception/postcondition change breaks substitutability, even though the precondition change alone would have been fine.

**Q11 (5 marks)**
A student wrote the following method in a `Controller` class:

```java
public double getDiscount(String customerId) {
  double discount = 0;
  for (Customer c : customers) {
    if (c.getId() == customerId) {
      if (c.getClass() == GoldCustomer.class) {
        discount = 0.2;
      } else if (c.getClass() == SilverCustomer.class) {
        discount = 0.1;
      } else if (c.getClass() == BronzeCustomer.class) {
        discount = 0.05;
      }
    }
  }
  return discount;
}
```

Identify **two** distinct code/design smells in this method, and explain how you would resolve each one.

> ### ✅ Model Answer
> **Smell 1: Type-checking via `getClass()` / conditional chains instead of polymorphism.** The method branches on the runtime class of `Customer` to decide behaviour. This violates the Open-Closed Principle — adding a new tier (e.g., `PlatinumCustomer`) requires editing this method rather than just adding a class.
> *Fix:* Give `Customer` (or an interface) an abstract `getDiscountRate()` method, and have each subclass override it with its own rate. `getDiscount()` then simply calls `c.getDiscountRate()` — no branching needed, and the method is closed to modification when new tiers appear.
>
> **Smell 2: `==` comparison on `String`s, and an inefficient linear scan doing two jobs at once.** Comparing `String customerId` with `==` compares references, not content — a latent correctness bug (should use `.equals()`). The method also mixes "find the customer" with "compute the discount," a mild SRP violation, and does an O(n) scan when a `Map<String, Customer>` keyed by ID would be O(1).
> *Fix:* Use `.equals()` for string comparison, and consider storing customers in a `Map<String, Customer>` for direct lookup; optionally extract "find customer by ID" into its own method so `getDiscount` has a single responsibility.

**Q12 (3 marks)**
```java
class Vehicle {
  public String describe() {
    return "A generic vehicle";
  }
}

class ElectricCar extends Vehicle {
  @Override
  public String describe() {
    return "An electric car";
  }
}

class Main {
  public static void main(String[] args) {
    ElectricCar car = new ElectricCar();
    Vehicle vehicle = car;
    System.out.println(vehicle.describe());
  }
}
```

What does this program print? Explain your answer with reference to dynamic (runtime) polymorphism and method dispatch.

> ### ✅ Model Answer
> The program prints **"An electric car"**.
>
> Even though the variable `vehicle` is declared with static type `Vehicle`, Java uses **dynamic (runtime) method dispatch** for overridden instance methods: the JVM looks at the actual runtime type of the object (`ElectricCar`) to decide which `describe()` implementation to invoke, not the compile-time/declared type of the reference. Since `ElectricCar` overrides `describe()`, that version runs regardless of the reference type used to call it. Static type only restricts *which methods you're allowed to call* at compile time; it never decides *which implementation actually runs*.

**Q13 (3 marks)**
A media company's video player currently only supports a single "standard" playback speed algorithm. The product team wants to add "1.5x", "2x", and slow-motion playback modes without modifying the existing player logic, and wants users to switch between playback modes at runtime.

Name the most appropriate design pattern for this situation and justify your choice by mapping the domain to the pattern's key structural characteristics.

> ### ✅ Model Answer
> The most appropriate pattern is the **Strategy Pattern**.
> - The "family of interchangeable algorithms" in Strategy maps directly onto the different playback-speed algorithms (standard, 1.5x, 2x, slow-motion).
> - Strategy encapsulates each algorithm behind a common interface (e.g., `PlaybackStrategy` with a `play()` method), so `VideoPlayer` composes/holds a reference to a `PlaybackStrategy` rather than implementing the logic itself.
> - This satisfies OCP: new playback modes are added as new classes implementing the interface, with **no changes** to `VideoPlayer`.
> - It satisfies "switch at runtime" because `VideoPlayer` can simply be given a different `PlaybackStrategy` object at any time (e.g., via a setter), rather than the mode being fixed at construction or requiring subclassing per mode.

**Q14 (5 marks)**
Explain the difference between **checked exceptions**, **unchecked (runtime) exceptions**, and **errors** in Java, including one example of each. Then, state the rule that governs which exceptions a subclass method may declare in its `throws` clause when overriding a superclass method, and explain why this rule exists.

> ### ✅ Model Answer
> - **Checked exception:** must be declared or handled at compile time; subclasses `Exception` but not `RuntimeException`. Example: `IOException`.
> - **Unchecked (runtime) exception:** not required to be declared/caught; subclasses `RuntimeException`. Example: `NullPointerException`.
> - **Error:** typically a serious system-level problem the program usually shouldn't try to catch; subclasses `Error`. Example: `OutOfMemoryError`.
>
> **Overriding rule:** a subclass method's `throws` clause may only contain exceptions that are the same as, or subtypes of, the exceptions declared in the superclass method's `throws` clause — i.e., it can only be a **subset**, never add new/broader checked exceptions.
>
> **Why:** this preserves the Liskov Substitution Principle. Client code written against the superclass's method signature only expects to handle the superclass's declared exceptions; if an override could throw new checked exceptions, client code substituting in the subclass would no longer compile or correctly handle all possible outcomes, breaking substitutability.

### Question 15 — Domain Modelling (10 marks)

A regional council wants a system to manage community sports leagues. The functional requirements are:

- A `League` has a series of `Team`s registered to it (e.g., "Eastside Eagles", "Riverside Rockets").
- Each `Team` has one or more `Player`s.
- Each `League` has an `Administrator`, who is a `Person`.
- Each `Team` has a `Coach`, who is also a `Person`.
- `Player`s can be added to or removed from a `Team`.
- A `League` schedules `Match`es between two `Team`s at a given `Venue`.

Model the domain for the above requirements as the basis of a software solution. Your answer should include:

- Interfaces, if applicable
- Class signatures, including inheritance relationships where appropriate
- Method signatures
- Key fields and relationships, including aggregations, compositions, and cardinalities (as comments)

You do **not** need to implement the bodies of any methods — stubs/prototypes only. Justify any non-obvious design decisions as comments or Javadoc.

**Marking breakdown:**
- Modelling of entities (4 marks)
- Aggregations, compositions and cardinalities (3 marks)
- Modelling of functionality (3 marks)

> ### ✅ Model Answer
>
> ```java
> /**
>  * Base class for any human participant in the system.
>  * Administrator and Coach both "are-a" Person, since they share
>  * identity attributes (name, contact info) but have different
>  * responsibilities within the domain.
>  */
> public abstract class Person {
>   private String name;
>   private String contactEmail;
>
>   public String getName() { return null; }
>   public String getContactEmail() { return null; }
> }
>
> public class Administrator extends Person {
>   // An Administrator manages exactly one League (1-to-1 from this side).
>   // Modelled as Association: Administrator can exist without a League
>   // currently assigned (e.g., between appointments).
> }
>
> public class Coach extends Person {
>   // A Coach manages exactly one Team at a time (1-to-1 from this side).
> }
>
> /**
>  * A League aggregates Teams: Teams could conceivably move between
>  * leagues (e.g., promoted/relegated to a different division) or exist
>  * in a "free agent pool" between seasons, so this is Aggregation,
>  * not Composition.
>  */
> public class League {
>   private String name;
>   private Administrator administrator; // 1 League -- 1 Administrator (composition: League owns this responsibility slot)
>   private List<Team> teams;            // 1 League o-- 0..* Team (aggregation)
>   private List<Match> matches;         // 1 League *-- 0..* Match (composition: matches are created and owned by their league)
>
>   public League(String name, Administrator administrator) {}
>
>   public void registerTeam(Team team) {}
>   public void removeTeam(Team team) {}
>
>   /**
>    * Schedules a match between two teams at a venue.
>    * Design decision: scheduling logic lives on League (not Team),
>    * since a Match is a League-level concept involving two Teams
>    * that shouldn't need to know about each other directly.
>    */
>   public Match scheduleMatch(Team home, Team away, Venue venue) { return null; }
> }
>
> /**
>  * A Team is composed of Players: a Player roster slot belongs to
>  * exactly one Team at a time in this domain (no multi-team players
>  * stated in the spec), so Player is modelled as strongly owned here.
>  * If cross-team players were needed later, this would move to
>  * Aggregation instead.
>  */
> public class Team {
>   private String name;
>   private Coach coach;          // 1 Team -- 1 Coach (composition: Team owns this responsibility slot)
>   private List<Player> players; // 1 Team *-- 1..* Player (composition)
>
>   public Team(String name, Coach coach) {}
>
>   public void addPlayer(Player player) {}
>   public void removePlayer(Player player) {}
> }
>
> public class Player extends Person {
>   private String position;
>
>   public String getPosition() { return null; }
> }
>
> /**
>  * A Match is owned by its League (composition — a Match cannot exist
>  * without the League that scheduled it) but only associates with its
>  * two Teams and a Venue (aggregation/association — Teams and the
>  * Venue exist independently of any one Match).
>  */
> public class Match {
>   private Team homeTeam; // Match o-- 1 Team (aggregation/association)
>   private Team awayTeam; // Match o-- 1 Team (aggregation/association)
>   private Venue venue;   // Match o-- 1 Venue (aggregation/association)
>
>   public Match(Team homeTeam, Team awayTeam, Venue venue) {}
>
>   public Team getHomeTeam() { return null; }
>   public Team getAwayTeam() { return null; }
>   public Venue getVenue() { return null; }
> }
>
> public class Venue {
>   private String name;
>   private String address;
>
>   public String getName() { return null; }
> }
> ```
>
> **Key design decisions (would be worth marks as Javadoc/comments in the actual answer):**
> - `Person` is abstract and shared by `Administrator`, `Coach`, and `Player` — avoids duplicating name/contact fields (an Is-a relationship, not Has-a).
> - `Team`–`Player` is composition (players don't exist independently of a team in this spec), while `League`–`Team` is aggregation (teams could plausibly move leagues).
> - `Match`–`Team`/`Venue` is aggregation/association, not composition, since teams and venues clearly outlive any single match.
> - No interfaces were strictly required by the spec (no obvious multiple/interchangeable implementations of any entity), but you could justify extracting a `Schedulable` interface if you wanted to note that decision explicitly — not doing so is also fine as long as you don't invent an unjustified interface just to "tick a box."

### Question 16 — Refactoring & Design Patterns (18 marks)

A junior developer built a `NotificationService` for an app that alerts users via different channels. The current (simplified) code looks like this:

```java
public class NotificationService {
  public void notifyUser(String channel, String message, String userContact) {
    if (channel.equals("EMAIL")) {
      System.out.println("Connecting to SMTP server...");
      System.out.println("Sending email to " + userContact + ": " + message);
    } else if (channel.equals("SMS")) {
      System.out.println("Connecting to SMS gateway...");
      System.out.println("Sending SMS to " + userContact + ": " + message);
    } else if (channel.equals("PUSH")) {
      System.out.println("Connecting to push notification service...");
      System.out.println("Sending push notification to " + userContact + ": " + message);
    }
  }
}
```

**a) Identify the design problem (2 marks)**
Briefly explain what is wrong with this design, with reference to a specific design principle.

**b) Choose a pattern (2 marks)**
Name the design pattern you would use to fix this problem, and briefly justify why it fits.

**c) Refactor (10 marks)**
Refactor `NotificationService` using your chosen pattern so that:
- A new channel (e.g., "SLACK") can be added **without modifying existing classes**.
- The class using the notification logic depends only on abstractions, not concrete channel implementations.

Write your solution as Java class/interface stubs (full signatures; method bodies may be simplified/pseudocode where the exact I/O logic isn't the focus).

**d) Extend the design (4 marks)**
The product team now wants to notify a user via **multiple channels simultaneously** for urgent alerts (e.g., both EMAIL and SMS), and wants to be able to compose channel combinations dynamically at runtime without creating a new class for every combination. Briefly explain how you would extend your design (you may name an additional pattern) to support this, and justify your choice.

> ### ✅ Model Answer
>
> **a) Design problem (2 marks)**
> `notifyUser()` branches on a `String channel` with an `if/else` chain, meaning every new channel requires **modifying** this existing method. This violates the **Open-Closed Principle** — the class is not closed to modification when new notification channels are introduced. It's also somewhat brittle/error-prone since `channel` is a raw `String` rather than a type-safe abstraction (a typo like `"EMAILL"` silently does nothing).
>
> **b) Pattern choice (2 marks)**
> The **Strategy Pattern** fits best: each channel (Email, SMS, Push) is an interchangeable algorithm for "how to send a notification," and `NotificationService` should depend on a common `NotificationChannel` abstraction rather than branching on channel type itself.
>
> **c) Refactor (10 marks)**
>
> ```java
> /**
>  * Strategy interface: each concrete channel implements its own
>  * sending logic behind this common abstraction.
>  */
> public interface NotificationChannel {
>   void send(String message, String userContact);
> }
>
> public class EmailChannel implements NotificationChannel {
>   @Override
>   public void send(String message, String userContact) {
>     System.out.println("Connecting to SMTP server...");
>     System.out.println("Sending email to " + userContact + ": " + message);
>   }
> }
>
> public class SmsChannel implements NotificationChannel {
>   @Override
>   public void send(String message, String userContact) {
>     System.out.println("Connecting to SMS gateway...");
>     System.out.println("Sending SMS to " + userContact + ": " + message);
>   }
> }
>
> public class PushChannel implements NotificationChannel {
>   @Override
>   public void send(String message, String userContact) {
>     System.out.println("Connecting to push notification service...");
>     System.out.println("Sending push notification to " + userContact + ": " + message);
>   }
> }
>
> /**
>  * A new channel (e.g., SlackChannel) can now be added by simply
>  * creating a new class implementing NotificationChannel -- no
>  * existing class needs to change. NotificationService depends only
>  * on the NotificationChannel abstraction, not concrete channels.
>  */
> public class NotificationService {
>   public void notifyUser(NotificationChannel channel, String message, String userContact) {
>     channel.send(message, userContact);
>   }
> }
>
> // Example of the new channel being added with zero changes elsewhere:
> public class SlackChannel implements NotificationChannel {
>   @Override
>   public void send(String message, String userContact) {
>     System.out.println("Connecting to Slack webhook...");
>     System.out.println("Sending Slack message to " + userContact + ": " + message);
>   }
> }
> ```
>
> **d) Extension for multi-channel + runtime composition (4 marks)**
> To notify via multiple channels at once, without creating a new class per combination, apply the **Composite Pattern** on top of the existing `NotificationChannel` interface:
>
> ```java
> /**
>  * A CompositeNotificationChannel treats a group of channels as a
>  * single NotificationChannel, delegating send() to each child.
>  * This lets callers compose any combination of channels at runtime
>  * (e.g., EMAIL + SMS for urgent alerts) without a new class per
>  * combination -- they just construct a Composite with the desired
>  * children.
>  */
> public class CompositeNotificationChannel implements NotificationChannel {
>   private List<NotificationChannel> channels = new ArrayList<>();
>
>   public void addChannel(NotificationChannel channel) {
>     channels.add(channel);
>   }
>
>   @Override
>   public void send(String message, String userContact) {
>     for (NotificationChannel channel : channels) {
>       channel.send(message, userContact);
>     }
>   }
> }
> ```
> This works because `NotificationService.notifyUser()` already depends only on the `NotificationChannel` abstraction — it can be handed a `CompositeNotificationChannel` exactly as if it were a single channel, with no changes needed to `NotificationService` itself. This is the classic Composite benefit: treating a group of objects uniformly with a single object of the same type.

### Question 17 — Programming with Streams & Generics (12 marks)

You are given a simplified `Order` class:

```java
public class Order {
  private String customerId;
  private double amount;
  private String status; // "PENDING", "SHIPPED", "CANCELLED"

  // constructor, getters omitted for brevity
}
```

**a) (4 marks)** Write a method `List<Order> getShippedOrders(List<Order> orders)` using the Stream API that returns only the orders with status `"SHIPPED"`.

**b) (4 marks)** Write a method `double totalRevenue(List<Order> orders)` using the Stream API that sums the `amount` of all `"SHIPPED"` orders only (treat this as a terminal/reduction operation).

**c) (4 marks)** Write a generic method `<T> Optional<T> firstMatching(List<T> items, Predicate<T> condition)` that returns the first item in `items` satisfying `condition`, or an empty `Optional` if none match. Briefly explain, in a comment, why using a bounded wildcard would or would not be appropriate here.

> ### ✅ Model Answer
>
> ```java
> import java.util.List;
> import java.util.Optional;
> import java.util.function.Predicate;
> import java.util.stream.Collectors;
>
> public class OrderUtils {
>
>   // a)
>   public static List<Order> getShippedOrders(List<Order> orders) {
>     return orders.stream()
>         .filter(order -> order.getStatus().equals("SHIPPED"))
>         .collect(Collectors.toList());
>   }
>
>   // b)
>   public static double totalRevenue(List<Order> orders) {
>     return orders.stream()
>         .filter(order -> order.getStatus().equals("SHIPPED"))
>         .mapToDouble(Order::getAmount)
>         .sum();
>   }
>
>   // c)
>   // A bounded wildcard (e.g., <T extends Comparable<T>>) is NOT
>   // appropriate here: this method places no constraint on what T
>   // can do (it never compares, orders, or otherwise operates on T
>   // beyond passing it to the given Predicate). An unbounded generic
>   // <T> is correct because the method must work for genuinely any
>   // type, and the Predicate<T> parameter already carries all the
>   // type-specific behaviour needed -- adding a bound would only
>   // needlessly restrict which types callers could use this with.
>   public static <T> Optional<T> firstMatching(List<T> items, Predicate<T> condition) {
>     for (T item : items) {
>       if (condition.test(item)) {
>         return Optional.of(item);
>       }
>     }
>     return Optional.empty();
>   }
> }
> ```
>
> *(Note: `firstMatching` could equally be written with `items.stream().filter(condition).findFirst();` — both are correct; the loop version is shown for clarity on what's happening under the hood.)*

**Q18 (4 marks)**
A university enrolment system has business domains like "Course Catalog", "Enrolment", and "Timetabling", and technical layers such as "User Interface", "Business Logic", and "Data Access". Describe how a **Monolithic Layered Architecture** would organise this codebase versus how a **Modular Monolith** would organise it. Which would better isolate the changes needed to add a new "Waitlist" feature? Justify your answer.

> ### ✅ Model Answer
> A **Monolithic Layered Architecture** organises code horizontally by technical concern — all UI code together, all business logic together, all data access together (e.g., `controllers/`, `services/`, `repositories/`). Adding "Waitlist" here means touching **three separate layers/folders** (a new controller endpoint, new service logic, new repository/data access code), each sitting alongside unrelated business logic for Catalog, Enrolment, etc.
>
> A **Modular Monolith** organises code vertically by business domain — each module (e.g., `enrolment/`, `catalog/`, `timetabling/`) is self-contained and internally has its own UI/logic/data layers. Adding "Waitlist" here likely means adding a new module (or extending the `enrolment` module) whose internals are isolated from the other domains via a clear module boundary/interface.
>
> **The Modular Monolith better isolates this change**, because the change is confined to one cohesive module rather than being scattered across shared, cross-domain layers. In the Layered architecture, the "Business Logic" layer especially risks becoming a large shared space where Waitlist logic sits next to unrelated logic, increasing the chance of unintended coupling or regressions in other domains.

**Q19 (3 marks)**
A logistics company wants to redesign its parcel-tracking platform. The system must react in real time to events from many independent sources (scanners, delivery vehicles, customer apps) and different downstream services need to respond to the same event (e.g., updating tracking status, notifying the customer, updating analytics) without those services being directly coupled to each other. Which architectural style discussed in the course is most suitable? Justify your answer with reference to the style's key characteristics.

> ### ✅ Model Answer
> **Event-Driven Architecture (EDA)** is most suitable.
> - The scenario has many independent event sources (scanners, vehicles, apps) — EDA is designed for this kind of asynchronous, multi-producer input.
> - Multiple downstream services (tracking status, notifications, analytics) need to react to the *same* event without being directly coupled to each other or to the producer — this is exactly the publish/subscribe decoupling EDA provides: producers emit events without knowing or caring who consumes them, and each consumer can be added/removed independently.
> - This also satisfies scalability and maintainability constraints, since new consumers (e.g., a future fraud-detection service) can subscribe to existing events without any change to the producers or other consumers.

**Q20 (5 marks)**
Explain the difference between an **event** and a **message** in the context of event-driven architecture, giving one example of each in the context of an online food delivery platform. Then name and briefly describe **two** of the "Fallacies of Distributed Systems" that are especially relevant to a team migrating from a monolith to a distributed, event-driven system.

> ### ✅ Model Answer
> **Event:** a broadcast that something has already happened, with no expectation of a response, e.g., `"OrderPlaced"` — any number of services (kitchen display, delivery dispatch, analytics) can listen without the order service knowing or caring who's listening.
> **Message:** a targeted instruction demanding a specific action from a specific recipient, e.g., a `"ChargePayment"` message sent directly to the Payment Service.
>
> **Two relevant fallacies:**
> - *"The Network Is Reliable"* — a team migrating from in-process monolith calls to network calls between services may assume calls always succeed, but network failures are now a real, frequent case that must be handled (retries, timeouts, idempotency).
> - *"Observability Is Optional"* — in a monolith, a stack trace shows the whole call path; in a distributed event-driven system, tracing a single business transaction across many decoupled services becomes far harder, so teams need dedicated tracing/logging infrastructure (e.g., OpenTelemetry) from the start, not as an afterthought.

**Q23 (10 marks) — Sequence Diagram**
Draw a sequence diagram using **mermaid syntax** for the following scenario:

> A customer places an order on an e-commerce site. The system checks product stock. If the product is in stock, it reserves the stock, charges the customer's payment method, and sends a confirmation email. If the product is out of stock, it notifies the customer that the order cannot be completed.

Your diagram should make appropriate use of `alt` (for the in-stock / out-of-stock branching) and clearly show all relevant participants (e.g., Customer, OrderService, InventoryService, PaymentService, EmailService).

> ### ✅ Model Answer
>
> ```mermaid
> sequenceDiagram
>     participant Customer
>     participant OrderService
>     participant InventoryService
>     participant PaymentService
>     participant EmailService
>
>     Customer->>OrderService: placeOrder(productId, paymentInfo)
>     OrderService->>InventoryService: checkStock(productId)
>     InventoryService-->>OrderService: stockStatus
>
>     alt product in stock
>         OrderService->>InventoryService: reserveStock(productId)
>         InventoryService-->>OrderService: reservationConfirmed
>         OrderService->>PaymentService: chargePayment(paymentInfo)
>         PaymentService-->>OrderService: paymentConfirmed
>         OrderService->>EmailService: sendConfirmationEmail(customerId)
>         EmailService-->>OrderService: emailSent
>         OrderService-->>Customer: orderConfirmed
>     else product out of stock
>         OrderService-->>Customer: orderFailed(outOfStock)
>     end
> ```
>
> **Why this shape:** every participant mentioned in the prose appears, in the order first involved. The `alt` block contains the entire multi-step happy path (reserve → charge → email → confirm), while `else` is a short single-step failure response — this "long happy path, short failure path" shape is the most common exam pattern for this question type.
