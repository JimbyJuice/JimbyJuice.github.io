## 1. Architecture vs. Design — the spectrum

**Definition.** Architecture and design sit on a spectrum, not in separate boxes:
- **Architecture (strategic):** high-impact, long-term, expensive-to-reverse decisions — e.g. migrating monolith→microservices, choosing a database technology, on-premises vs. cloud.
- **Design (tactical):** low-impact, short-term, cheap-to-reverse, code-level decisions — e.g. changing a button colour, applying a Strategy pattern to clean up one class.

**How to tell which one a decision is (the actual test, not a vibe):**
- **Scope & impact** — does this affect the whole system, or one local piece of it?
- **Level of effort to reverse** — if this turns out wrong, is undoing it a small edit or a multi-month migration?
- **Trade-offs** — does it involve system-wide characteristic trade-offs (e.g. availability vs. maintainability), or just local code quality?

**Design-thinking question for an exam scenario:** *"If this decision turns out to be wrong in six months, what does fixing it cost?"* Cheap fix → design question, answer with a pattern from Weeks 4–5. Expensive, system-wide fix → architecture question, answer with a style/characteristic trade-off from this document.

**Exam relevance.** A short-answer question may describe a decision and ask you to classify it as architectural or tactical and justify why — use exactly this three-part test (scope, cost-to-reverse, system-wide trade-offs) rather than just asserting an answer.

## 2. Architectural Characteristics (the "-ilities")

**Definition.** The qualities and constraints a system's architecture must support — *how* the system performs under constraints, as distinct from **logical components**, which represent *what* the system does (its domain behaviour). A "User Registration" component (what) must support "Scalability" (how) under concurrent signups.

### 2.1 The four categories

| Category | Meaning | Examples |
|---|---|---|
| **Process** | Intersection of architecture and development practice | Deployability (ease/frequency of safe releases), Maintainability (ease of fixing/extending without regressions) |
| **Structural** | Internal modular design | Modularity (how well-partitioned the code is), Coupling (how tightly bound different parts are) |
| **Operational** | Runtime execution qualities | Scalability, Availability, Reliability, Elasticity, Responsiveness |
| **Cross-cutting** | Span multiple facets at once | Security, Accessibility |

### 2.2 Composite characteristics

Some high-level characteristics are actually bundles of simpler, more measurable ones — if a question asks you to "break down" a characteristic, this is the move:
- **Reliability = Availability + Consistency + Data Integrity**
- **Resilience = Robustness + Fault Tolerance + Recoverability**

### 2.3 Implicit vs. explicit requirements

- **Explicit:** stated directly in requirements ("must support French and Japanese" → Internationalisation).
- **Implicit:** unstated but expected, requiring domain knowledge to infer (24/7 uptime, data security) — these are the ones exam scenarios expect you to *infer*, not the ones handed to you directly.

**How to triangulate implicit characteristics from a scenario (three lenses — use all three, not just one):**
1. **Problem domain (feature-driven):** what does the *kind* of system inherently demand? A multiplayer game needs low latency → Responsiveness. An e-commerce flash sale needs to absorb sudden load → Elasticity.
2. **Environmental awareness (organisational constraints):** a startup needs to ship fast → Deployability/Agility. A legacy enterprise team needs to plug into existing systems → Integrability.
3. **Holistic domain knowledge (compliance/industry standards):** banking needs Auditability & Security; healthcare needs Confidentiality & Data Integrity.

**Design-thinking question:** *"If this scenario doesn't explicitly say what quality matters, what industry/domain is it in, and what does that industry always implicitly demand?"* This is a high-yield exam move — implicit-characteristic questions are specifically testing whether you can read between the lines using domain knowledge, not whether you memorised a list.

### 2.4 From characteristic to structural consequence

Each characteristic *demands* specific structural choices — this is the link between "we need X" and "therefore we build Y":

| Characteristic | Structural demand |
|---|---|
| Security | Encryption layers, role-based access control, audit trails |
| Scalability | Sharded databases, load balancers, stateless services |
| Availability | Failover mechanisms, redundant nodes, data replication |
| Responsiveness | Edge caching, async queuing/event processing |
| Elasticity | Auto-scalers, container orchestration |

### 2.5 Trade-offs — you cannot maximise everything

This is the single most exam-relevant idea in this section: enhancing one characteristic degrades another, and that's not a design flaw, it's the actual job.

| Trade-off | Why |
|---|---|
| Security vs. Performance | Encryption/token validation adds latency |
| Scalability vs. Simplicity | High scale needs distributed styles (sharding, microservices) — more moving parts |
| Availability vs. Maintainability | Redundant failover setups complicate upgrades/testing |
| Responsiveness vs. Consistency | Real-time speed often relies on eventual consistency over immediate transactional consistency |
| Flexibility vs. Performance | Plugin/config layers add indirection and latency |

**Exam move (repeat this pattern in every architecture justification):** *"Choosing [style] gives us [characteristic A], at the cost of [characteristic B], which is [acceptable/unacceptable] here because [scenario detail]."* Never claim a style is just "better" — name what it costs.

## 3. Architectural Decision Records (ADRs)

**Definition.** A structured document capturing the *why* behind a strategic decision, so future readers don't see it as arbitrary.

**The seven sections (reproduce this structure in an exam answer, don't blend them into prose):**
1. **Title** — short, numbered, descriptive.
2. **Status** — Proposed / Accepted / Superseded / RFC.
3. **Context** — the forces, constraints, business context, and alternatives considered.
4. **Decision** — the explicit, assertive choice ("We will use...").
5. **Consequences** — honest trade-offs, both positive and negative.
6. **Compliance** — how the decision's adherence is monitored (code review, automated fitness functions).
7. **Notes** — author, approvers, dates.

**Worked example, reasoned through (Online Auction System — Bid Capture forwarding to Bid Streamer and Bid Tracker):**

*Context:* Bid Capture needs to forward incoming bids to two downstream services without lag or state corruption. Options considered: single pub/sub topic, point-to-point queues, or synchronous REST.

*Decision:* separate, dedicated point-to-point queues for Bid Streamer and Bid Tracker.

*Reasoning worth internalising, not just memorising the answer:*
- **One-way flow:** Bid Capture doesn't need a response back, so async messaging (non-blocking) fits better than synchronous REST, which would force Bid Capture to wait on two slow downstream calls per bid.
- **Ordering requirement:** Bid Streamer must display bids in exact received order — point-to-point FIFO queues guarantee this natively; a shared pub/sub topic with multiple independent consumers doesn't guarantee the same delivery order to each consumer without extra coordination.
- **State decoupling:** Bid Streamer only cares about the *first* bid at a given amount (duplicates irrelevant to it); Bid Tracker needs *all* bids. A single shared topic would force Bid Streamer to implement its own duplicate-filtering logic and hold shared in-memory state it shouldn't need to know about — separate queues let each consumer only see what it actually needs.
- **Backpressure:** Bid Tracker writes to a slow database; its queue absorbing that slowness (rather than a shared topic) prevents a slow consumer from creating pressure that affects Bid Streamer's fast in-memory-cache-backed consumption.

*Consequences (honestly stated, not hidden):* requires clustering infrastructure for high availability; Bid Capture must publish to multiple queues instead of one; internal bid events bypass API gateway security checks — an accepted trade-off given the internal-only nature of this traffic.

**Why this example is worth internalising as a template, not just memorising:** notice the *shape* of the reasoning — each design choice is justified by tracing it back to a specific *requirement* (ordering, independent consumer needs, backpressure isolation), not asserted as "queues are better." This is the reasoning shape an exam ADR-style question rewards.

## 4. C4 Model — Context & Container (this course's scope)

> **Scope note (from your own material):** this course focuses *strictly* on Context (Level 1) and Container (Level 2) — Component and Code diagrams exist in the full C4 framework but aren't in scope here. Don't spend exam time drawing Component-level detail unless explicitly asked.

### 4.1 Context Diagrams

Shows your system in relation to the outside world — **no internal detail**.

**Three entity types:**
- **Person** — anyone interacting with the system (name + `[person]` + short description). Multiple people only if they interact *distinctly differently* (a rideshare app has Customers and Drivers — different interaction patterns, not just different purposes).
- **Software System** — the one system you're designing (exactly one box).
- **Existing/External System** — something your system depends on that already exists (e.g. Google Maps in a delivery tracker).
- **Relationships** — arrows with a short description of the interaction; mostly system↔external, occasionally external↔external.

### 4.2 Container Diagrams

Breaks the single system box into its **major deployable/runtime units** — web apps, mobile apps, APIs, databases, microservices, message buses. Not classes, not code — still a high-level diagram aimed at infrastructure/deployment planning.

**Five container types:** Frontend (web/mobile app), Database, Microservice, Message Bus (used specifically when modelling Event-Driven Architecture), and a generic "Regular" container for anything else.

**Process for converting Context → Container:**
1. Copy the context diagram, replace the system box with an **enterprise box** (containing everything you're about to add), delete relationships *to* the system for now (keep external↔external relationships intact).
2. Decide what containers exist inside the system.
3. Re-add relationships, but now pointing to the *specific container* responsible for that interaction, not the system as a whole.

**Design-thinking question for choosing containers:** *"What are the genuinely separately-deployable pieces here? Would I actually build and release this piece independently of that one?"* If two "containers" would always be deployed together with no independent lifecycle, they're probably one container, not two.

### 4.3 Law of Demeter and coupling metrics, applied at the architecture scale

Your material extends the Law of Demeter (Weeks 4–5) up to the component/container level: a component should only communicate directly with its immediate neighbours — this is the same "friend of a friend" reasoning from `checkValidEnrolment`, now applied to services instead of objects.

**Afferent vs. efferent coupling:**
- **Afferent coupling (Ca)** — incoming dependencies: how many other components depend on *you*.
- **Efferent coupling (Ce)** — outgoing dependencies: how many other components *you* depend on.
- **Total coupling = Ca + Ce.** Lower total coupling across domain boundaries reduces fragility (a component with high Ca is risky to change — many things depend on it; a component with high Ce is fragile to others' changes).

**Design-thinking question:** *"If I need to change this component's public interface, how many other components does that ripple into (Ca)? If a dependency of mine changes, how many places does that break me (Ce)?"*

## 5. Architectural Styles

### 5.1 Two independent dimensions

Your material's key organising idea: styles aren't one flat list — they vary along **two independent dimensions**, and understanding this is what lets you reason about *why* a style has the properties it has, rather than memorising properties in isolation.

**Dimension 1 — Partitioning concern:**
- **Technical partitioning:** organised by technical role — Presentation / Business Logic / Persistence layers. (Analogy: restaurant staff split by role — host, wait staff, chef, busser.) *Pro:* clear division of labour, easy role specialisation. *Con:* a single domain change (e.g. a new product category) cascades vertically through every layer, since each layer only knows its technical role, not the business concept.
- **Domain partitioning:** organised by business capability — Order, Inventory, Payment, Shipping modules. (Analogy: a food court — independent stalls, each a complete specialisation.) *Pro:* high change isolation (a change to Order rarely touches Shipping), maps directly to team ownership. *Con:* risk of duplicated utility logic across domains; cross-domain integration gets complex.

**Dimension 2 — Deployment model:**
- **Monolithic:** one deployable package. *Pro:* simple setup, low ops cost, easy local debugging, high reliability (no network calls between internal parts). *Con:* can't scale one part independently — scaling means scaling everything; "all-or-nothing" outage risk.
- **Distributed:** independent processes communicating over a network. *Pro:* independent scaling, strong fault isolation, modular team ownership. *Con:* network complexity, harder debugging, higher infra cost, distributed transaction complexity.

**Why this matters for reasoning about unfamiliar styles:** any named style is really a *specific combination* of a partitioning choice and a deployment choice. Layered = technical + monolithic. Modular Monolith = domain + monolithic. Microservices = domain + distributed. Once you see it this way, you can reason about a style you've never been explicitly taught by asking "what partitioning, what deployment, and what does that combination imply?"

### 5.2 Fallacies of Distributed Computing

**Why this list matters:** every one of these is a false assumption that leads teams into architecture mistakes when adopting a distributed style — this is effectively "the specific ways distributed deployment's downsides show up in practice," and is a strong source of exam short-answer content ("what could go wrong if...").

The network is reliable · Latency is zero · Bandwidth is infinite · The network is secure · Topology doesn't change · There is one administrator · Transport cost is zero (infra/routing/gateway costs compound into high TCO) · The network is homogeneous (diverse vendors/firmware cause real compatibility breaks) · Latency is non-existent · Bandwidth is static · Observability is optional (without centralised logging/distributed tracing, debugging async distributed failures becomes effectively impossible).

**Design-thinking question:** *"If a scenario proposes going distributed, which of these fallacies is the scenario's author implicitly assuming away, and what breaks if that assumption is wrong?"*

### 5.3 Detailed style comparison

| Style | Partitioning | Deployment | DB rule | Key benefit | Critical drawback |
|---|---|---|---|---|---|
| **Layered** | Technical | Monolithic | Single shared DB | Simple, fast to build, familiar (MVC-like) | Heavy change cascading; DB becomes the scaling bottleneck |
| **Modular Monolith** | Domain | Monolithic | Physically shared, logically partitioned schemas | High performance (no network latency) + domain alignment + team ownership | Module boundaries are easily bypassed (IDE auto-imports); needs strict discipline to hold |
| **Microservices** | Domain | Distributed | One physical DB per service (bounded context) | Independent scaling, strong fault isolation, high agility | High operational complexity, distributed tracing difficulty, data consistency challenges |
| **Event-Driven** | Domain/reactive | Distributed (usually paired with microservices) | Event channels (queues/pub-sub/topics) | Parallel execution, high responsiveness, extensibility, fault tolerance | Very hard to trace/debug; monitoring overhead |

**Critical misconception to avoid (explicitly flagged in your material):** Event-Driven Architecture is **not** a deployment topology on the same level as Monolith/Microservices — it's a *programming/communication style* that can be layered onto either. A Modular Monolith can internally use event-driven patterns (in-process events) without being distributed at all. Layered, Modular Monolith, and Microservices, by contrast, **are** mutually exclusive deployment topologies — you pick exactly one of those three for a given system.

### 5.4 Deep dive: Modular Monolith database discipline

Because a modular monolith shares one physical database but must preserve domain isolation, three rules enforce the boundary:
1. **Logical partitioning** — separate schemas per module within the same database.
2. **No foreign keys across modules** — reference another module's records by **ID only** (e.g. store a `RecipeItemID`, not a foreign-key relationship into the Recipe module's table).
3. **No SQL JOINs across module tables** — if the Order module needs Recipe details, it must call the Recipe module's **public API** at runtime, not query its tables directly.

**Why this matters conceptually (tie back to Weeks 4–5):** this is the Law of Demeter and encapsulation, applied at the database/module scale — "no direct joins across boundaries" is structurally identical to "don't reach through an object into its collaborator's internals." The smell this discipline prevents is called **Inappropriate Intimacy** — modules (or objects) that know far too much about each other's internal representation.

### 5.5 Deep dive: Microservice granularity

**Granularity disintegrators (forces pushing services *smaller*):**
- **Cohesion** — unrelated behaviours shouldn't share a service.
- **Fault tolerance** — isolate unstable/crash-prone features (e.g. a flaky email service) so their failure doesn't take down stable ones.
- **Access control** — strict security needs (e.g. credit card processing) demand isolation from lower-sensitivity data.
- **Code volatility** — isolate high-churn code from stable runtimes.
- **Scalability** — isolate high-load features so they scale independently of low-load ones.

**Granularity integrators (forces pushing services *larger*/merged):**
- **Database transactions** — distributed transactions are hard to keep ACID; merging tightly-coupled transactional operations (e.g. `OrderCreation` + `InventoryDeduction`) avoids needing a distributed transaction at all.
- **Data dependencies** — merging fields/services that are always read/written together avoids chatty, excessive network calls.
- **Workflow efficiency** — grouping steps that would otherwise require many peer-to-peer network hops into one service.

**Design-thinking question, the actual exam-relevant skill here:** *"For this specific pair of operations, does keeping them in separate services buy meaningful fault-isolation/scaling benefit, or does it just create a distributed transaction / chatty-network problem I don't need?"* — granularity questions want you to weigh a *specific* disintegrator against a *specific* integrator for the scenario given, not recite the two lists.

### 5.6 Deep dive: Orchestration vs. Choreography

Two ways to coordinate a business workflow across multiple microservices:

| | Orchestration | Choreography |
|---|---|---|
| Structure | A central orchestrator directs each service on what to do | Services independently listen to events and react |
| Analogy | Symphony conductor | Peer-to-peer event dance |
| Pros | Centralised state, easy tracing, simple error handling | Scalable, loosely coupled, highly responsive |
| Cons | Orchestrator can become a bottleneck / single point of failure / highly coupled | Complex error management and state tracking (no one place shows the whole flow) |

**Recognition trigger:** "who is responsible for knowing the overall sequence of steps?" — if the scenario wants a single traceable place to see/control the whole flow, orchestration; if it wants maximum decoupling and independent evolution of each service, choreography.

### 5.7 Deep dive: Serverless (FaaS)

**BaaS vs. FaaS distinction:** BaaS (Backend-as-a-Service) = renting hosted infrastructure (e.g. managed auth, storage) to avoid hardware maintenance. FaaS/Serverless = on-demand, stateless function execution triggered purely by events.

**Core design principles:**
- **Stateless** — functions can't rely on local in-memory state between invocations; must persist to external storage (S3, DynamoDB-style stores).
- **Event-driven** — triggered by events, not long-lived REST loops.
- **Minimal & composable** — single responsibility per function.
- **Decoupled flows** — leverage queues/pub-sub rather than direct calls between functions.

**Trade-offs:**
- **Cold starts** — idle functions pay initialisation latency on first trigger, especially severe for JVM/.NET runtimes; mitigated by provisioned concurrency or warm-up polling (which itself adds cost).
- **Long-lived connections** — unsuitable for protocols needing persistent sockets (video streaming, real-time gaming).
- **Cost at scale** — for constant, high-baseline workloads, per-invocation serverless billing can exceed the cost of just running dedicated VMs.
- **Latency** — unsuitable for hard low-latency requirements, given cold-start risk.

**Common misconception (explicitly flagged):** serverless is not simply "always faster/cheaper" — it wins specifically for *bursty, infrequent, event-triggered* workloads, and loses for *constant, latency-sensitive, or stateful* ones.

## 6. Worked Lab/Tutorial-Style Examples — What Concept Each Demonstrates

### 6.1 "Moodle-style" Course Management System (Context/Container modelling)

**What the exercise demonstrates:** translating plain-English requirements (Students view/submit assessments and get grades; Instructors create/grade assessments and manage students; infrastructure includes a web frontend, backend API, SQL database, SSO/Auth integration, async email service) directly into Context (people + external systems + your one system) and Container (the deployable pieces: web app, API, database, auth server as external, email service) diagrams.

**Key design decisions worth reasoning through, not just copying:**
- **Decoupling UI from backend** (a React-style webapp talking to a separate API container) — this keeps the frontend portable and independently scalable/replaceable from backend concerns, the same "swap the implementation without touching the interface" idea from black-box ADT design in Weeks 1–3, now applied at container granularity.
- **State partitioning** — the database is deliberately the *only* stateful runtime container. If the API or webapp container restarts, it returns to a clean slate with no data loss, because nothing important was held in that container's memory. This is a direct structural consequence of "Availability demands failover/redundancy" (section 2.4) — stateless containers are trivially replaceable/restartable, which is what makes redundancy cheap.

**Transferable skill:** given *any* set of user stories, practise the pattern "who are the distinct people (by interaction pattern) → what's the one system → what external systems does it depend on (Context) → what are the genuinely independently-deployable pieces inside it (Container)."

### 6.2 Tutorial: Banks vs. Microservices (stale data risk)

**The question posed:** can a commercial banking platform use asynchronous, event-driven microservices to settle international wire transfers?

**The answer, and why it's the right answer (not just "no"):** highly distributed event-driven systems trade immediate consistency for availability/responsiveness — under this model, account balances may be briefly stale between services. For financial transfers, staleness isn't an acceptable trade — the correctness requirement (exact, immediately-consistent balances) outweighs the availability/responsiveness benefit distributed event-driven design would otherwise provide.

**What this demonstrates:** a live instance of the CAP-theorem-style tension between consistency and availability/responsiveness (section 2.5's trade-off table), and a case where the "obviously more scalable/modern" answer (microservices) is the *wrong* answer once you weigh the actual dominant requirement of the domain.

**Transferable skill/exam trigger:** whenever a scenario involves money, medical dosing, or anything where a stale read causes real-world harm (not just inconvenience), treat "immediate consistency" as the dominant, non-negotiable requirement, and be willing to argue *against* the trendier distributed option.

### 6.3 Assignment-style: code smells → modular monolith transition

**Pattern demonstrated:** "Duplicated Code / Switch Statements on Type" as a smell leads to OCP violations — refactor with **Strategy** (direct callback to Weeks 4–5). "Inappropriate Intimacy" (direct cross-module database access) is the architecture-scale version of Feature Envy/Law of Demeter — refactor by enforcing Public APIs and logically separated schemas (section 5.4's rules), which is the mechanism that turns a layered "big ball of mud" into a disciplined Modular Monolith.

**Transferable skill:** recognise that Weeks 4–5's smell vocabulary doesn't stop applying once you're at architecture scale — Feature Envy/Law of Demeter reappears as Inappropriate Intimacy between modules; DRY-violating switch-on-type reappears as OCP-violating branching that Strategy still fixes, just now potentially at a service-selection level rather than a single-class level.

## 7. Exam-Critical Reasoning Chains

**The master template — reproduce this shape whenever asked to evaluate/improve a design:**
```
Real-world scenario
      ↓
Design issue / bottleneck (what's actually going wrong, concretely)
      ↓
Violated design principle (name it: OCP, SRP, Law of Demeter, ACID/consistency, etc.)
      ↓
Identified code/architecture smell (Inappropriate Intimacy, Big Ball of Mud, switch-on-type, ...)
      ↓
Proposed refactoring action (what structurally changes)
      ↓
Applicable pattern, if any (Strategy, Observer, Facade, Factory, ...)
      ↓
Improved, decoupled architecture (name the resulting style/topology)
```

**Case study 1 — Real-Time Multiplayer Lobby.** Issue: slow DB writes + REST polling bottleneck matchmaking responsiveness. Principle violated: OCP (matchmaking tightly coupled to the database). Smell: Inappropriate Intimacy (components querying each other's data directly). Refactor: extract matchmaking into its own service, hold active queues in a fast in-memory cache. Pattern: replace REST polling with **Observer**-style push notifications (WebSockets) — clients get notified of state changes rather than repeatedly asking. Resulting architecture: event-driven, point-to-point queues.

**Case study 2 — Fast-Growing E-Commerce Platform.** Issue: payment, inventory, and notifications are one tightly-coupled monolith; a bug in email delivery crashes checkout. Principle violated: SRP at the application level — no modular boundaries. Smell: Big Ball of Mud. Refactor: split the shared database into logically isolated domain schemas with ID references (section 5.4); restrict cross-module interaction to public APIs. Pattern: **Facade** as each module's interface; **Factory** to create module-specific API adapters. Resulting architecture: transition from Layered monolith to Modular Monolith.

**Case study 3 — Bank Wire Transfers.** Issue: financial operations need strict consistency; a distributed architecture's eventual consistency risks discrepancies. Principle violated: ACID guarantees across service boundaries. Smell: Feature Envy (services constantly fetching each other's account details over REST just to compute something). Refactor: merge account data, currency validation, and ledger into one cohesive component (a granularity *integrator* case, section 5.5). Pattern: **Strategy** for swapping transfer-validation algorithms by destination country. Resulting architecture: stay monolithic with a shared schema, prioritising immediate consistency over distributed scalability — directly reflecting the Tutorial 9 conclusion (6.2).

**Why these three are worth internalising as templates, not just memorising the answers:** notice each one resolves differently (event-driven / modular monolith / stay-monolithic) despite all three "sounding like" they should modernise toward microservices — the correct answer in each case comes from tracing the *specific* dominant characteristic (responsiveness / independent team ownership / consistency) back through the trade-off table in section 2.5, not from a general "microservices are more modern" instinct.

## 8. Common Exam Misconceptions (explicitly flagged in your material)

1. **"Event-Driven Architecture is a deployment style like Monolith/Microservices."** False — it's a *communication/programming style* orthogonal to deployment topology. A Modular Monolith can use event-driven patterns internally without being distributed. Layered, Modular Monolith, and Microservices *are* mutually exclusive deployment choices, but EDA isn't a fourth option in that same list.
2. **"Every modern system should use microservices from day one."** False — the operational overhead (network latency, distributed transactions, infra cost) is a real cost that small teams/domains shouldn't pay without a genuine reason (section 5.2's fallacies are exactly the ways this backfires).
3. **"Serverless is always faster/cheaper."** False — cold starts (especially JVM/.NET) and high-baseline-load billing can make it slower and more expensive than the alternative; it wins specifically for bursty, infrequent, stateless workloads.
4. **"Vertical spacing in a sequence diagram represents elapsed time."** False — sequence diagrams show chronological *order* only, never duration. Don't try to encode timing via spacing.
