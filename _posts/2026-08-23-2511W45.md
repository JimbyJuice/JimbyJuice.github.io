### 1.1 Code smell vs. design problem — the distinction your own course material draws

Your Enrolment lab opens with a distinction worth internalising word-for-word, because it reframes how you should answer *every* "identify the problem" question for the rest of the course: a code smell is how you **detect** that something is wrong; the design problem is the underlying issue **causing** the smell. Smelling rotten food tells you food has gone off; the smell isn't the problem, the spoiled food is.

**Why this distinction is graded, not pedantic:** if an exam question asks "what design principle is violated," answering with just the smell ("there's a weird conditional" or "this method reaches into another object's data") loses marks — you need to name the *principle* (Feature Envy, Law of Demeter, SRP, LSP, tight coupling) that the smell is symptomatic of, because that's what tells you *how* to fix it.

### 1.2 Feature Envy / "Tell, Don't Ask" — reasoning through `hasPassedCourse()`

Your Part A snippet:

```java
public boolean hasPassedCourse() {
    if (grade == null) {
        return false;
    }
    return grade.getMark() >= 50 && grade.getGrade() != "FL" && grade.getGrade() != "UF";
}
```

**Reasoning it out, rather than pattern-matching to a name:** ask *"whose data is this method mostly working with?"* `hasPassedCourse()` lives on `Enrolment`, but almost every line of its body is spent pulling values out of `grade` (`getMark()`, `getGrade()` twice) and computing a judgement about *Grade's* data. `Enrolment` is reaching across an object boundary to do work that's arguably `Grade`'s own responsibility to know about itself. This is the smell called **Feature Envy** — a method that seems more interested in another class's data than its own — and it's a symptom of a violated principle sometimes phrased as **"Tell, Don't Ask"**: rather than asking `grade` for its raw fields and computing a judgement externally, `Enrolment` should simply *tell* `grade` to answer the question itself (`grade.isPassing()`).

**The design-thinking question this generalises to:** *"Does this method use another object's data more than its own? If I deleted this method and had to rewrite it from scratch, which class's fields would I be reaching into the most — and is that the class this method actually belongs on?"*

**The second, independent issue in the same snippet** (a genuine, easy-to-miss bug, not just a style smell): `grade.getGrade() != "FL"` compares `String`s with `!=`, which compares **object references**, not content — exactly the pointer-vs-value distinction from `equals()` in Weeks 1–3. Two `String`s holding `"FL"` are not guaranteed to be reference-equal (this depends on Java's string interning behaviour, which is not something a correct program should ever rely on for equality). The fix isn't just moving the logic to `Grade` — the comparison itself needs to become `!grade.getGrade().equals("FL")` (which is exactly what the final `Grade.isPassing()` does in the codebase you were given).

**Why the refactor (moving the logic into `Grade.isPassing()`, and having `Enrolment.hasPassedCourse()` delegate to it) is better, not just "correct":** it fixes the reference-equality bug in exactly one place instead of everywhere this logic might be duplicated, and it means `Grade` — the class that actually owns `mark`/`grade` — is now the sole authority on what "passing" means. If the passing threshold changes later (say, to `>= 45`), there is exactly one method to update.

**Connections.** This is a live instance of encapsulation from Weeks 1–3, taken further: it's not enough for fields to be `private` — the *behaviour that interprets those fields* should generally live alongside them too.

### 1.3 Law of Demeter / Principle of Least Knowledge — reasoning through `checkValidEnrolment`

**Definition.** An object should only directly "talk to" its immediate collaborators — itself, its own fields, its method parameters, and objects it creates — not reach through one collaborator to manipulate or query *its* internals.

**The candidate in your codebase, reasoned through:**

```java
private boolean checkValidEnrolment(Student student) {
    return getCoursePrereqs().stream().allMatch((prereq) ->
        student.getEnrolments().stream()
            .filter((e) -> e.getCourse().equals(prereq))
            .anyMatch(Enrolment::hasPassedCourse)
    );
}
```

This method lives on `CourseOffering`. Ask: *what is `CourseOffering` doing here?* It's reaching into `student.getEnrolments()` (a collection that conceptually belongs to `Student`), then filtering and interrogating each individual `Enrolment` inside that collection to figure out whether the student has passed a given prerequisite. `CourseOffering` has become intimately familiar with *how `Student` tracks its own enrolment history* in order to answer a question that is really about the student — "has this student passed this course?" is a question `Student` should be able to answer about itself, directly.

**Signal that tipped this off as a violation (rather than ordinary collaboration):** the chain doesn't stop at asking `student` a question — it asks `student` for its internal collection, and then goes on to independently filter/interrogate the *elements* of that collection. That's the "friend of a friend" pattern the Law of Demeter warns against — CourseOffering isn't just talking to its direct collaborator `Student`, it's operating on `Student`'s internals as if they were its own.

**The refactor (reasoned, not reproduced in full):** introduce a method on `Student` — something like `hasPassed(Course course)` — that encapsulates "search my own enrolments for this course and check if I passed it" inside `Student` itself. `CourseOffering.checkValidEnrolment` then becomes a much shorter, flatter expression: for each prerequisite, ask the student directly whether they've passed it, with no reaching into `Student`'s internal list from the outside.

**Why this is better than just "shorter code":** `Student`'s internal representation of its enrolment history (currently a `List<Enrolment>`) becomes free to change (e.g., to a `Map<Course, Enrolment>` for faster lookup) without needing to touch `CourseOffering` at all — exactly the "localise the impact of change" payoff encapsulation is meant to provide, now applied one level higher, between collaborating classes rather than within a single class.

**Design-thinking question:** *"Am I calling a method on an object I obtained from another object, in order to interrogate its internals — or am I asking a direct collaborator a well-named question and trusting it to answer for itself?"*

### 1.4 Liskov Substitution Principle — reasoning through the Bank Account hierarchy

**Definition.** If `S` is a subtype of `T`, objects of type `T` should be replaceable with objects of type `S` without altering the correctness of the program — i.e., any code written against the supertype's contract must keep working, unmodified, when handed a subtype instance instead.

**The Design-by-Contract formulation (this is the version that makes LSP checkable, not just a vague vibe):** a subclass may only **weaken preconditions** (accept everything the parent accepted, or more) and **strengthen or preserve postconditions** (guarantee everything the parent guaranteed, or more) for any overridden method. If a subclass *tightens* a precondition (rejects inputs the parent would have accepted) or *weakens* a postcondition (guarantees less than the parent promised), it breaks substitutability — code written against the parent's contract can no longer safely call the method on a subclass instance.

**Walking through your three subclasses using exactly this test — the `deposit`/`withdraw` contracts, straight from your own Javadoc:**

`BankAccount.withdraw`: `@pre amount > 0 && amount <= balance`.

- **`DefensiveBankAccount.withdraw`**: same stated precondition (`amount > 0 && amount <= balance`), but now *enforces* it by throwing `IllegalArgumentException` instead of leaving behaviour undefined on violation. The precondition itself is unchanged — a caller who was already honouring `BankAccount`'s contract sees identical behaviour; only callers who were already violating the contract (and therefore had no behavioural guarantee at all under DbC) now get a defined, informative failure instead of silent corruption. This does **not** violate LSP — the accepted input set hasn't shrunk.
- **`LoggedBankAccount.withdraw`/`deposit`**: precondition unchanged; postcondition is *extended* (balance changes exactly as before, **and now** a log entry is guaranteed to be added) — strengthening a postcondition (promising more) is explicitly allowed under LSP. A caller expecting only the balance-change guarantee is unaffected by the extra guarantee they didn't ask for.
- **`SwissBankAccount.withdraw`/`deposit`**: `@pre amount > 1000 && amount <= balance` — this **tightens** the precondition from `amount > 0` to `amount > 1000`. This *is* an LSP violation: code written against `BankAccount`'s contract might reasonably call `account.deposit(50)`, which is perfectly valid for the general contract — but if that `account` reference actually points to a `SwissBankAccount`, this previously-valid call now fails. Substituting a `SwissBankAccount` where a `BankAccount` was expected changes the correctness of code that relied only on the supertype's documented contract.

**Design-thinking question, generalisable to any exam scenario with an inheritance hierarchy and Javadoc contracts:** *"Compare the `@pre` of the override to the `@pre` of the method it overrides — has the set of acceptable inputs grown, shrunk, or stayed the same? Do the same comparison for `@post`."* Shrinking the accepted-input set (tightened precondition) or promising less (weakened postcondition) is the two-part test for an LSP violation.

The `BankAccount` example above demonstrates the same underlying test (precondition/postcondition comparison) that applies regardless of which codebase it's found in.

### 1.5 Contract-first design and immutability — the Rational Numbers exercise

**What this exercise is teaching, beyond "implement a fractions class":** you were deliberately handed a client (`FunFractions`) written against a contract that doesn't exist yet, specifically to force you to design the contract *before* the implementation — the exercise's own framing makes the point explicit: Attila "didn't consult with you to come up with an interface, or contract" and his code doesn't compile as a result. This is Design by Contract applied at the scale of an entire class API, not just a single method: **the contract (method signatures + preconditions + postconditions + invariants) is the actual point of collaboration between the class's author and its client**, and should be agreed/specified before either side commits to an implementation.

**Two design points worth extracting explicitly:**

1. **Precondition placement, reasoned through the spec's own words:** *"You do not need to handle zero denominators or any cases of division by zero."* This is DbC in action — rather than defensively checking for a zero denominator inside every method (constructor, `divide`, etc.), the responsibility is explicitly pushed onto the caller: it becomes a precondition (`denominator != 0` on construction; `divisor != 0` on `divide`) that you *document*, not code around. This is the same reasoning your Bank Account lab's prerequisite summary lays out: offload responsibility to the caller rather than bloating every method with checks, when the context makes that a reasonable trade-off (an internal teaching-game class, not operating-system code handling untrusted input).

2. **Immutability as a design choice, not an implementation accident:** *"The `add`, `subtract`, `multiply` and `divide` methods should all work as expected on two `Rational` objects and return a new `Rational` instance without modifying the originals."* This is worth pausing on: it would be entirely possible to implement `add` by mutating `this`'s numerator/denominator and returning `this`. The spec explicitly forbids that. **Why does this matter?** If `Rational` were mutable, then `Rational total = a.add(b)` would be ambiguous about whether `a` itself changed — every caller holding a reference to `a` elsewhere in the program would need to worry whether some other code's `add` call silently altered the value they were relying on. Immutable value objects remove an entire category of bugs (aliasing bugs) by making it structurally impossible for one part of a program to unexpectedly change a value another part depends on. This is your first deliberate encounter with a **functional-programming value**, ahead of the Functional Paradigm section proper (1.7) — expressions that produce new values rather than statements that mutate existing ones.

**Design-thinking question for any class you're asked to design from a spec:** *"Before I write a single method body, what does this class promise to guarantee, and what does it require of its caller to make that guarantee possible? Could I write this contract down as Javadoc `@pre`/`@post` before I've written any implementation at all?"*

### 1.6 Coupling — reasoning through the gspread example and `StudentPortal`

**The gspread comparison, reasoned through rather than just answered:** `sheet.worksheets()[1]` accesses a tab by **position** in a list; a name-based lookup accesses it by an explicit, stable **identifier**. Ask: *what happens to each approach if someone inserts a new tab at the front of the spreadsheet, or reorders tabs?* The index-based lookup silently starts pointing at the wrong tab — its correctness is **coupled to an implementation detail (ordering) that has nothing to do with the actual thing being referenced** and can change for reasons entirely unrelated to the code that depends on it. The name-based lookup is coupled only to the tab's identity, which is the thing that's actually semantically stable. **General principle:** prefer coupling your code to the most stable, most semantically meaningful thing available — an explicit identifier almost always beats an incidental position.

**Applying the same lens to `StudentPortal`/`CourseOffering` (Q4):** `enrolInCourse` takes a `zid` and a `courseCode` (Strings) rather than `Student` and `Course` objects directly, and re-derives the objects via linear search (`findStudent`, a loop over `courses`) every time. Reasoning through the trade-off rather than declaring a verdict:

- **Argument for using object references directly** (lower coupling to a *format*, higher coupling to the *object graph*): if `enrolInCourse` instead took `Student` and `Course` objects, the caller does the lookup once, and `StudentPortal` doesn't need to repeatedly re-search its own collections just to convert an ID back into an object it may have handed out identifiers for in the first place.
- **Argument for using ID strings** (looser coupling to the object graph, tighter coupling to a stable format): if `StudentPortal` is meant to be a boundary a client interacts with *without* holding onto live object references (e.g., a web API layer where the caller only ever has a zID string from a request, not a live `Student` object in memory), string IDs are the natural, decoupled interface — the client shouldn't need to hold a reference to internal domain objects at all.

**Design-thinking question:** *"Is the caller of this method a fellow class inside the same object graph (favour passing objects directly), or a boundary/external caller that shouldn't be expected to hold domain object references (favour stable identifiers)?"* There often isn't a single universally-correct answer — a good exam response identifies the trade-off and justifies a choice for the *specific* scenario given, rather than declaring one approach categorically superior.

### 1.7 The Functional Paradigm — from loops to pipelines

**Definition.** Functional-style code expresses computation as a composition of pure(-ish) transformations over data (`map`, `filter`, `reduce`/`collect`), rather than as a sequence of statements that mutate variables in a loop.

**Why it exists.** The procedural/functional comparison given in your material makes the contrast concrete:

```java
// Procedural — explicit mutation and control flow
List<Integer> discountedPrices = new ArrayList<Integer>();
for (Integer item : prices) {
    if (item < 20) {
        discountedPrices.add(item / 2);
    } else {
        discountedPrices.add(item - 5);
    }
}

// Functional — the same computation as a declarative pipeline
List<Integer> discountedPrices = prices.stream()
      .map(item -> ((item < 20) ? (item / 2) : (item - 5)))
      .collect(Collectors.toList());
```

The procedural version requires you to read every line to reconstruct *what* is being computed, because the "what" is entangled with the "how" (an explicit accumulator list, an explicit loop, an explicit `.add()` call). The functional version states the transformation directly: "map each price through this pricing rule." Fewer moving parts means fewer places for a mutation-related bug to hide (no accumulator variable to forget to initialise, no index to get wrong, no risk of mutating `prices` itself by accident).

**Reasoning through the real target, `checkValidEnrolment` — before-and-after, focusing on *why* each stream method was chosen, not just that streams were used:**

Conceptually, the imperative version of the underlying logic looks like:

```java
private boolean checkValidEnrolment(Student student) {
    for (Course prereq : getCoursePrereqs()) {
        boolean passed = false;
        for (Enrolment e : student.getEnrolments()) {
            if (e.getCourse().equals(prereq) && e.hasPassedCourse()) {
                passed = true;
                break;
            }
        }
        if (!passed) {
            return false;
        }
    }
    return true;
}
```

Compare this to the functional version already in your codebase:

```java
private boolean checkValidEnrolment(Student student) {
    return getCoursePrereqs().stream().allMatch((prereq) ->
        student.getEnrolments().stream()
            .filter((e) -> e.getCourse().equals(prereq))
            .anyMatch(Enrolment::hasPassedCourse)
    );
}
```

**Why each choice of stream method is the *correct* one, not just *a* stylistic option:**

- `allMatch` for the outer loop, because the original imperative logic returns `false` the moment *any single* prerequisite is unsatisfied — "every prerequisite must be satisfied" is a direct English match for `allMatch`, and it also gives you **short-circuiting for free**: it stops as soon as one prerequisite fails, exactly like the imperative version's early exit via the `if (!passed) return false;`.
- `anyMatch` for the inner check, because the original logic only needs to find *one* passing enrolment for that prerequisite — it doesn't need to know how many, or check all of them; `anyMatch` again short-circuits, matching the `break` in the imperative loop.
- `filter` before `anyMatch`, rather than combining both conditions inside one predicate, keeps "which enrolments are for this course" and "did the student pass it" as two separately-readable steps.

**Design-thinking question for converting a loop to streams:** *"What is this loop actually testing for — existence of a match (`anyMatch`), universal satisfaction (`allMatch`), transformation of every element (`map`), or selection of a subset (`filter`)? Name that first, then pick the stream method that says exactly that in English — don't reach for `.forEach()` with an `if` inside it as a default, since that's just a loop wearing a stream's syntax without gaining any of the declarative benefit."*

**Common mistake:** converting a loop to a stream purely for brevity, when the loop has side effects that make a "declarative" reading misleading (e.g., a `.forEach()` that mutates external state) — this doesn't achieve the actual goal of functional style (expressing computation without hidden mutation), it just hides the mutation inside a lambda.

### 1.8 Strategy Pattern — `Comparable` vs. `Comparator`, reasoned as one running example

**Definition.** The Strategy pattern encapsulates a family of interchangeable algorithms behind a common interface, so the algorithm used can be selected or swapped independently of the code that uses it.

**Recognising it in your own codebase, rather than being told it's there:** `Student implements Comparable<Student>` bakes in exactly **one** ordering (`compareTo` by `zid`) as an intrinsic property of the class — every piece of code that sorts `Student`s via their natural ordering gets zID order, permanently, unless it opts out. But `studentsEnrolledInCourse()` needs a *completely different* ordering (program, then stream count, then name, then zID) for one specific use case. If `Student`'s natural ordering were the only option, you'd have no way to get this second ordering without either mutating `compareTo` itself (breaking every other caller relying on zID order) or manually writing a bespoke sort routine outside the type system.

**This is precisely the problem Strategy solves:** `Comparator<T>` is the "algorithm" interface — any object implementing it is an interchangeable *sorting strategy* that can be handed to `sorted(...)` at the call site, completely independent of whatever `Comparable` ordering (if any) the type has baked in. `Comparable` gives a type **one default strategy**; `Comparator` lets you supply **any number of alternative strategies from outside the class**, chosen per call-site.

**The two implementation styles you were asked to compare are two different syntaxes for the *same pattern*, not two different patterns:**

```java
// Style A — classic OOP Strategy: an explicit class implementing the algorithm interface
Comparator<Student> byMultipleFields = new Comparator<Student>() {
    @Override
    public int compare(Student a, Student b) {
        // ... explicit field-by-field comparison logic ...
    }
};

// Style B — functional Strategy: the same interface, composed from smaller functions
Comparator<Student> byMultipleFields = Comparator
    .comparingInt(Student::getProgram)
    .thenComparingInt(s -> s.getStreams().length)
    .thenComparing(Student::getName)
    .thenComparing(Student::getZid);
```

Both are `Comparator<Student>` instances — interchangeable strategies you can pass to `.sorted(...)`. The difference is entirely in *how* you construct the strategy: Style A writes out the comparison logic imperatively inside an anonymous class; Style B composes the strategy declaratively out of smaller, named, reusable sub-comparators (this is the Functional Paradigm from 1.7, applied directly to constructing a Strategy object).

**The reasoning framework for judging which is "better" here (rather than a verdict handed to you):**

- Readability of *intent*: does the code read as "sort by program, then stream count, then name, then zID" at a glance, or do you have to trace through an imperative `if`/`return` chain to reconstruct that ordering?
- Extensibility: how much code changes if a fifth tiebreaker field is added?
- Reusability of sub-strategies: can `Comparator.comparing(Student::getName)` be reused elsewhere on its own, independent of this specific multi-field chain?
- Boilerplate: how much scaffolding (the anonymous class declaration, the `@Override`) exists purely to satisfy Java's syntax, versus expressing the actual comparison logic?

Apply these four lenses yourself to reach a justified answer, rather than memorising "functional is always better" — there are legitimate cases (very complex, branching comparison logic that doesn't decompose cleanly into `thenComparing` chains) where an explicit class reads more clearly.

**Exam-recognition trigger for Strategy in an unfamiliar scenario:** any time a class needs to support *multiple interchangeable ways of doing the same kind of operation*, selectable at runtime or per call-site (sorting orders, discount calculations, validation rules, pricing rules) — if you find yourself wanting to pass "a way of doing X" as a parameter, that parameter's type should usually be a Strategy interface.

**Distinguishing Strategy from a simple `if`/`switch`:** an `if`/`switch` picks between hard-coded behaviours *inside* one method, and adding a new behaviour means editing that method. Strategy lets you add a new behaviour by writing a brand-new class/lambda that implements the existing interface — the method that *uses* the strategy never needs to change. If you find yourself repeatedly editing the same `if`/`switch` every time a new "kind of algorithm" is needed, that's the signal to extract it into a Strategy interface instead.

### 1.9 Composite Pattern

> **Additional clarification — not evidenced in your uploaded lab material.** This is standard, commonly COMP2511-taught content, but I don't have a lab exercise of yours to teach it through, so the example below is a generic, clearly-labelled illustration rather than something drawn from your codebase. Cross-check terminology against your actual lecture slides.

**Definition.** Composite lets you compose objects into tree structures representing part-whole hierarchies, and treat an individual object and a composition of objects **through the same interface**, so client code doesn't need to distinguish "a single leaf" from "a group of things" when performing an operation.

**Problem it solves.** Without Composite, client code that needs to operate on "either one item or a collection of items, possibly nested" ends up littered with type checks (`if (thing instanceof Group) { for (child : thing.getChildren()) ... } else { ... }`), and that logic has to be duplicated everywhere the tree is traversed.

**Structure:**

- `Component` — a common interface both individual items and groups implement (e.g., `render()`, `getSize()`).
- `Leaf` — an individual item with no children; implements `Component` directly, operation applies to itself only.
- `Composite` — a group holding a collection of child `Component`s (which may themselves be `Leaf`s or further `Composite`s); implements `Component` by delegating/aggregating the operation across its children.

**Generic Java example (file-system sizes — a standard illustrative case, not from your course):**

```java
public interface FileSystemEntry {
    long getSize();
}

public class File implements FileSystemEntry {
    private long sizeBytes;
    @Override
    public long getSize() { return sizeBytes; }
}

public class Folder implements FileSystemEntry {
    private List<FileSystemEntry> contents = new ArrayList<>();
    @Override
    public long getSize() {
        return contents.stream().mapToLong(FileSystemEntry::getSize).sum();
    }
}
```

A caller computing `entry.getSize()` never needs to know or check whether `entry` is a `File` or a `Folder` — nested folders-within-folders are handled automatically by the recursive delegation in `Folder.getSize()`, and a client asking for the size of the whole tree, a subtree, or a single file all use the exact same method call.

**Recognition trigger.** A scenario describes a hierarchical/nested part-whole structure (folders containing files and folders; UI components containing other components; an organisation chart of employees who may themselves manage teams) **and** an operation that needs to apply uniformly whether you're looking at a single item or an arbitrary-depth group of them.

**When NOT to use it.** If the hierarchy is shallow and fixed (never more than one level deep, and unlikely to change), or if leaves and composites genuinely need very different operations that can't be meaningfully unified behind one interface, the extra abstraction of a shared `Component` interface may cost more in indirection than it saves.

**Distinguishing from a plain `List<T>` traversal:** if every element of the collection is homogeneous and there's no recursive part-whole nesting (no "a group can contain other groups"), you don't need Composite — a `List<T>` and a loop already treat every element uniformly. Composite specifically earns its keep when the structure is recursive.

### 2.1 Observer Pattern & Event-Driven Programming

> **Additional clarification — not evidenced in your uploaded lab material.** Standard content, generic example below, grounded loosely in your existing domain for continuity, but this specific scenario wasn't literally in your labs.

**Definition.** Observer defines a one-to-many dependency where a **subject** maintains a list of **observers** and notifies them automatically of relevant state changes, without needing to know anything concrete about who those observers are or what they'll do in response.

**Problem it solves.** Without Observer, the object where a change happens has to explicitly know about, and directly call, every other piece of code that cares about that change — coupling the subject to every consumer, and requiring the subject's code to change every time a new kind of consumer is added.

**Structure:**

- `Subject`/`Observable` — holds a collection of observers, exposes `subscribe(Observer)`/`unsubscribe(Observer)`, and calls `notify(...)` on each observer when a relevant change occurs.
- `Observer` — an interface with an `update(...)`-style method the subject calls; concrete observers implement whatever reaction they need.

**Illustrative (not-from-your-labs) example, grounded in your Enrolment domain for continuity:**

```java
public interface GradeObserver {
    void onGradeRecorded(Student student, Grade grade);
}

public class Enrolment {
    private List<GradeObserver> observers = new ArrayList<>();
    public void subscribe(GradeObserver observer) { observers.add(observer); }

    public void setGrade(Grade grade) {
        this.grade = grade;
        for (GradeObserver observer : observers) {
            observer.onGradeRecorded(student, grade);
        }
    }
}
```

Now a `TranscriptGenerator`, a `GraduationEligibilityChecker`, and an `EmailNotifier` could all subscribe as independent `GradeObserver`s — `Enrolment` never needs to know any of them exist, or change its own code when a new kind of observer is added. Compare this to the alternative without Observer: `setGrade` would need to directly call `transcriptGenerator.update(...)`, `eligibilityChecker.check(...)`, `emailNotifier.send(...)` explicitly, coupling `Enrolment` to every consumer's concrete class.

**Relationship to event-driven programming.** Observer is the object-oriented pattern; "event-driven programming" is the broader architectural style built on the same idea at a larger scale — a system structured around emitting and reacting to events (UI click handlers, message queues, webhooks) rather than a fixed, linear call sequence. Observer is essentially event-driven programming applied within a single object's API.

**Recognition trigger.** A scenario where "many different things need to react when X happens, and X shouldn't need to know what those things are" — especially where the list of reactions is expected to grow over time, or where different deployments/configurations want different reactions subscribed.

**When NOT to use it.** If there's exactly one, fixed consumer that will never change, a direct method call is simpler and more traceable than the indirection Observer introduces (you lose the ability to just "follow the call" when reading the code — you have to know who's subscribed).

### 2.2 Decorator Pattern — motivated directly by your Bank Account hierarchy's limitation

**Definition.** Decorator lets you attach additional behaviour to an individual object dynamically, by wrapping it in another object that implements the same interface, without altering the wrapped object's class or affecting other instances of the same class.

**The problem, made concrete by code you've actually written:** your Bank Account lab gives you `DefensiveBankAccount`, `LoggedBankAccount`, and `SwissBankAccount`, each as a **separate subclass** of `BankAccount`. This works fine as long as you only ever need *one* of these behaviours at a time. But now ask the design-thinking question: *"What happens when a requirement changes to need a combination?"* — suppose the bank wants an account that is **both** defensive **and** logged. Single inheritance in Java means a class has exactly one superclass, so `LoggedDefensiveBankAccount extends LoggedBankAccount, DefensiveBankAccount` isn't legal Java. Your only options with subclassing alone are: duplicate the defensive checks *and* the logging inside one new subclass (violating DRY, exactly the smell from Weeks 1–3's `Room` example), or keep creating a new subclass for every combination you might need (`LoggedDefensiveAccount`, `LoggedSwissAccount`, `DefensiveSwissAccount`, `LoggedDefensiveSwissAccount`...) — a combinatorial explosion: *n* independent behaviours require up to 2ⁿ subclasses to cover every combination.

**This is exactly the problem Decorator exists to solve:** instead of baking each variant into a fixed position in an inheritance tree, make the base type an **interface**, and make each behaviour (defensive checking, logging, minimum-transaction enforcement) a separate **decorator class** that wraps *any* object implementing that interface and adds its behaviour before/after delegating to the wrapped object. Decorators can then be **composed at runtime**, in any combination and order, without a new class needed per combination.

**Structure:**

- `Component` — the shared interface (`BankAccount` as an interface: `deposit`, `withdraw`, `getBalance`).
- `ConcreteComponent` — the base implementation with no extra behaviour (a plain `BasicBankAccount`).
- `Decorator` — an abstract class that also implements `Component` and holds a reference to a wrapped `Component`, delegating calls to it by default.
- `ConcreteDecorator`s — each adds one specific behaviour before/after delegating (`LoggingDecorator`, `DefensiveDecorator`).

**Sketch of the restructure (illustrating the idea, not a full solution):**

```java
public interface BankAccount {
    void deposit(double amount);
    void withdraw(double amount);
    double getBalance();
}

public abstract class BankAccountDecorator implements BankAccount {
    protected final BankAccount wrapped;
    protected BankAccountDecorator(BankAccount wrapped) { this.wrapped = wrapped; }
    public void deposit(double amount) { wrapped.deposit(amount); }
    public void withdraw(double amount) { wrapped.withdraw(amount); }
    public double getBalance() { return wrapped.getBalance(); }
}

public class LoggingDecorator extends BankAccountDecorator {
    public LoggingDecorator(BankAccount wrapped) { super(wrapped); }
    @Override
    public void deposit(double amount) {
        wrapped.deposit(amount);
        // log the transaction
    }
    // withdraw() overridden similarly
}

public class DefensiveDecorator extends BankAccountDecorator {
    public DefensiveDecorator(BankAccount wrapped) { super(wrapped); }
    @Override
    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException(...);
        wrapped.deposit(amount);
    }
    // withdraw() overridden similarly
}
```

Now `new LoggingDecorator(new DefensiveDecorator(new BasicBankAccount(0)))` gives you a defensive **and** logged account, composed at the point of use, with **zero** new classes needed for that specific combination — and the order of wrapping is itself meaningful and controllable (defensive-then-logged behaves differently in edge cases from logged-then-defensive, which is a genuinely useful thing to be able to control explicitly).

**Trade-offs.** You now have more, smaller classes, and debugging requires tracing through a chain of wrapped delegations rather than one flat class — readability of "what does this object actually do" can suffer if decorators are stacked many layers deep without care.

**When NOT to use it.** If you genuinely only ever need one fixed behaviour variant (no combinations required, ever) — plain inheritance or even a single class with a boolean flag may be simpler and Decorator would be over-engineering.

**Distinguishing Decorator from Strategy:** Strategy swaps out **one interchangeable algorithm** wholesale (you have exactly one active strategy at a time); Decorator **layers/composes multiple behaviours** around a base object, and the layers can stack. If the question is "which one of several algorithms should I use," think Strategy; if it's "which combination of independent behaviours should I add on top," think Decorator.

**Exam trigger wording:** "add optional/combinable behaviours to an object," "avoid a subclass for every combination," "wrap an existing object to add behaviour without modifying its class."

### 2.3 Factory Patterns

> Your `StudentPortal.addCourse`/`addStudent` methods are a genuine, lab-evidenced example of the *motivation* behind Factory patterns (encapsulating creation), but they don't demonstrate the full Factory Method pattern (which specifically involves *polymorphic* creation, decided by subclasses). I've distinguished the two below so you don't conflate them.

**The motivation, grounded in your own code:**

```java
public Course addCourse(String courseCode, String title) {
    Course newCourse = new Course(courseCode, title);
    courses.add(newCourse);
    return newCourse;
}
```

Rather than every caller writing `new Course(...)` and separately remembering to add it to `StudentPortal`'s internal list, this method centralises both the construction and the registration in one place. This is the core Factory motivation at its simplest: **hide object creation behind a method, so callers depend on a stable operation rather than on `new` plus a concrete class name plus any bookkeeping that needs to happen alongside creation.** If creating a valid `Course` later needed extra steps (validating `courseCode` format, checking for duplicates), there's exactly one place to add that logic, and every existing caller of `addCourse` benefits automatically.

**Where this differs from the full Factory Method pattern (Additional clarification):** the textbook **Factory Method** pattern goes one step further — it defines an abstract "creator" with a method like `createProduct()` that returns some `Product` interface, and lets *subclasses* of the creator decide which concrete `Product` implementation gets instantiated, without the calling code ever needing to know the concrete type. For example:

```java
public abstract class ClubCreator {
    public abstract Club createClub(String name); // subclasses decide the concrete type
}

public class SocialClubCreator extends ClubCreator {
    @Override
    public Club createClub(String name) { return new SocialClub(name); }
}

public class SportsClubCreator extends ClubCreator {
    @Override
    public Club createClub(String name) { return new SportsClub(name); }
}
```

The key difference from `addCourse`: `addCourse` always creates exactly one hard-coded type (`Course`); Factory Method exists specifically for situations where **which concrete type gets created varies**, and you want that decision made polymorphically (by which creator subclass you're using) rather than via an `if`/`switch` on a type parameter.

**Recognition trigger for full Factory Method (vs. a simple creation-encapsulating method):** the scenario involves creating one of *several possible concrete types* that share a common interface, and you want adding a new type to require adding a new creator subclass rather than editing existing branching logic (this is the same "switching on type" smell reasoning from Weeks 1–3's `Room`/`isDesired` example, but applied to the *creation* step rather than a query method).

**Abstract Factory (Additional clarification, brief):** one level up again — a factory that creates a **family of related objects** that must be used together (e.g., a UI toolkit's `DarkThemeFactory` producing a matching dark-themed button, checkbox, and window, versus a `LightThemeFactory` producing the light-themed equivalents of all three) — ensuring the products created together are always a consistent, compatible set.

**When NOT to use a full Factory Method/Abstract Factory:** if there's only ever one concrete type being created (as in `addCourse`), a plain constructor or a simple creation method is sufficient — introducing an abstract creator hierarchy for a single concrete product is unjustified indirection.

### 2.4 Singleton Pattern

> **Additional clarification — not evidenced in your uploaded lab material.**

**Definition.** Singleton ensures a class has exactly one instance, accessible via a well-known global access point, typically by making the constructor private and exposing a static accessor.

```java
public class ConfigManager {
    private static ConfigManager instance;
    private ConfigManager() { /* load config */ }

    public static ConfigManager getInstance() {
        if (instance == null) {
            instance = new ConfigManager();
        }
        return instance;
    }
}
```

**Problem it solves.** Some resources genuinely only make sense to have one of throughout a program's lifetime — a single point of configuration, a single connection pool, a single logging sink — and Singleton guarantees that constraint at the type level rather than relying on every part of the codebase to voluntarily cooperate.

**Why it's taught with a caution attached, and why "when NOT to use it" matters more here than for most patterns:** Singleton introduces **global mutable state** into a program — any code, anywhere, can reach the single instance and (if it's mutable) change something that every other part of the program depends on, which is precisely the kind of hidden coupling the rest of Weeks 4–5 teaches you to avoid. It also makes **testing harder**: a class that depends on `ConfigManager.getInstance()` internally can't easily be tested with a different, controlled configuration, because the dependency isn't passed in — it's silently pulled from a global. A design that instead passes the shared instance in as a constructor/method parameter (dependency injection, even in its simplest form) keeps the "only one instance in production" property achievable by convention, while remaining fully testable and not smuggling in hidden global state.

**Design-thinking question before reaching for Singleton:** *"Do I actually need to guarantee, at the type-system level, that only one instance can ever exist — or do I just happen to only be creating one instance right now, in which case an ordinary object passed around explicitly (dependency injection) achieves the same practical outcome without the global-state cost?"* Most scenarios described as "just use one shared object" don't actually require the enforcement Singleton provides — they just need one instance to be *constructed once and passed around*, which doesn't need the pattern's static-accessor machinery at all.

**Thread-safety (brief, since Async is next).** The naive `getInstance()` above is not thread-safe — two threads could both see `instance == null` simultaneously and construct two separate instances. Standard fixes (synchronising the accessor, or eagerly initialising the instance as a `static final` field at class-load time) trade off lazy initialisation against synchronisation overhead/simplicity.

### 2.5 Asynchronous Design

> **Additional clarification — not evidenced in your uploaded lab material; kept intentionally brief since it's a broad topic without lab grounding to teach it through concretely.**

**Definition.** Asynchronous design lets a program start a potentially slow operation (a network call, a disk read, a long computation) without blocking the calling thread until it finishes, instead registering what should happen once the result becomes available.

**Why it exists.** A program that blocks its main/UI thread on every slow operation becomes unresponsive for the operation's entire duration. Asynchronous design lets other work (UI updates, other requests) continue concurrently while the slow operation completes in the background.

**Relationship to Observer/event-driven programming (2.1):** the most common way to consume an asynchronous result is precisely the Observer shape — you register a callback ("notify me when this is done") rather than waiting synchronously for a return value. Java's `CompletableFuture` formalises this:

```java
CompletableFuture<Grade> future = fetchGradeAsync(studentId);
future.thenAccept(grade -> System.out.println("Received: " + grade));
// program continues immediately; thenAccept's callback runs later, when the result arrives
```

This is structurally an Observer relationship — `future` is the subject, `thenAccept`'s lambda is the observer being notified of a "state changed" event (the result became available).

**Trade-offs.** Asynchronous code is harder to reason about sequentially (execution order isn't a straightforward top-to-bottom read of the source), and introduces genuine risks around shared mutable state accessed from multiple concurrently-running callbacks (race conditions) — exactly the class of risk Singleton's global-mutable-state caution (2.4) compounds if a Singleton is accessed from async callbacks without synchronisation.

**Design-thinking question:** *"Does this operation need to complete before the next line of my program can correctly proceed, or can the rest of the program usefully continue while this happens in the background?"* If the latter, that's the signal an operation is a candidate for asynchronous design rather than a plain blocking call.

### Cross-Week Reasoning Chain

> A requirement changes: an account type now needs **both** logging and defensive checking
> → the existing design (one subclass per behaviour) can't express this combination without a new subclass

### Common Mistakes Across These Weeks

- Naming a smell ("this method reaches into another object's fields") without naming the underlying principle it violates (Feature Envy / Law of Demeter / SRP) — exam answers need the principle, not just the observation.
- Treating `!=` as valid for `String` content comparison — a genuine bug, not a style nitpick, and one that resurfaces constantly in code-analysis questions.
- Checking only whether a subclass's precondition is *different*, rather than specifically whether it's *stronger* (rejects more) — LSP violations are about the *direction* of the change, not mere difference (postconditions can be strengthened safely; preconditions cannot).
- Converting every loop to a stream reflexively, including ones with side effects, without checking whether the result is genuinely more declarative or just syntactically shorter.
- Reaching for Singleton whenever "there's only one instance in practice," without asking whether the enforcement and global-state cost are actually needed, versus just constructing one instance and passing it around.
- Confusing Strategy (one algorithm active at a time, swapped wholesale) with Decorator (multiple behaviours layered/composed together) — both involve "an interface with multiple implementations," but the *shape* of how they're used differs.
- Introducing a full Factory Method hierarchy for a single concrete product type, when a plain constructor or simple creation method (like `addCourse`) is sufficient.

2. Given a Javadoc-annotated method and an override, you can apply the precondition-widens/postcondition-strengthens test to determine an LSP violation, without needing to "feel" that something's wrong.
