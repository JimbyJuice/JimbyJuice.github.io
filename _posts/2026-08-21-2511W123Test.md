## Section 1 — Answers

1. **C.** `getClass()` restricts equality to the exact same runtime type on both sides, which is what preserves symmetry (`a.equals(b) == b.equals(a)`) across a hierarchy — `instanceof` lets a subclass instance satisfy a superclass's `instanceof` check asymmetrically.
2. **B.** A `dateOfBirth` is part of identity, fixed at creation — same reasoning as `StaffMember.name`/`hireDate` in your Week 1 material. (A is wrong because reschedulable implies a setter is *needed*; C and D describe fields that legitimately mutate.)
3. **B.** Shared state/behaviour across implementers, with only one genuinely varying piece → abstract class, exactly the `Room` refactor reasoning.
4. **C.** The part (`Book`) cannot exist independently of the whole (`Library`) — composition.
5. **B.** DbC's core idea: a precondition violation is the caller's fault; the method need not behave sensibly, and an unchecked exception is a defensible signal of that.
6. **B.** `NullPointerException extends RuntimeException` (unchecked); `IOException extends Exception` (checked).
7. **C.** By definition — testing only through the observable public interface.
8. **B.** Identical structure to the pre-refactor `isDesired()`: redundant branches all reducing to `t == this.memberType`.

## Section 2 — Model Answers

**Q1 (3 marks).** Suppose `Vehicle.equals()` uses `instanceof Vehicle`, and `Car extends Vehicle` also uses `instanceof Vehicle` (or even `instanceof Car`, if it only compares `Vehicle`-level fields plus its own). A `Vehicle v` and a `Car c` with matching shared fields could then have `v.equals(c) == true` (since `c instanceof Vehicle`), but `c.equals(v) == false` (since `v` is not `instanceof Car`, or fails a stricter check) — violating `x.equals(y) == y.equals(x)`. *(1 mark for the mechanism, 1 mark for a concrete pair of classes, 1 mark for explicitly naming symmetry.)*

**Q2 (4 marks).**
(a) A precondition: `amount` must be positive (as stated in the Javadoc); implicitly, `target` should not be null.
(b) If `true`: the amount has been deducted from this account's balance and added to `target`'s balance.
(c) If `false`: this account's balance is unchanged (no partial transfer occurred), and `target`'s balance is unchanged.
(d) A plausible invariant: an account's balance is never negative (this is *why* the method can fail and return `false` rather than always succeeding).
*(1 mark each, accept reasonable equivalents.)*

**Q3 (3 marks).** The smell: an unnecessary intermediate variable (`member`), initialised to `null` and populated inside a switch purely to be added once afterwards — identical to `Hotel.addRoom` Code A. Problem: it introduces a moment where `member` is `null`/invalid, and if `type` doesn't match any case (e.g. a future enum value added without updating this switch), `members.add(null)` executes silently, corrupting the list — a bug the direct-add version (Code B) cannot produce. *(1 mark identifying the smell, 2 marks for the reasoning about risk/maintainability.)*

**Q4 (4 marks).** `Gym`–`Trainer`: **aggregation** — a `Trainer` can exist independently and be reassigned to a different `Gym` or none, so the "part" outlives/is-shareable-from the "whole." `Gym`–`Room`: **composition** — a `Room` has no independent existence outside its owning `Gym`; deleting the `Gym` deletes its `Room`s. *(2 marks each, must include the "can it exist/be reassigned independently" justification, not just the label.)*

**Q5 (4 marks).** Because black-box tests only exercise the class's public methods, they encode an assumption only about *observable behaviour*, not about how that behaviour is achieved internally. This means the internal implementation can be completely restructured (different fields, different algorithms, different class splits) and the tests remain valid as long as the public behaviour is unchanged — which is the exact definition of a refactor. If tests instead inspected private state directly, they would fail after any internal restructuring even when the public behaviour was correctly preserved, giving false signals and discouraging refactoring. *(Look for: the "why" — decoupling tests from implementation — not just a restatement of the definition.)*

**Q6 (4 marks).** As a standalone method, a missing config file is a foreseeable, recoverable condition for a well-behaved caller (e.g. the file might not have been created yet, or the path is user-supplied) — this argues for a **checked** exception, forcing every caller to have a plan. However, if an earlier step in the *same* program has already validated the file exists immediately before this call, then a failure at this exact point becomes a symptom of a broken precondition/race condition/programming error in that immediate context, which leans toward **unchecked** being defensible *at that specific call site* — though the method itself, since it may be called from many places with different guarantees, should still generally declare the checked exception, since it can't assume every caller has done that validation. *(Full marks require recognising both the general case and the caller-context-dependent nuance — this question deliberately mirrors the `UNSWNullPointerException` reasoning from archaic_fs.)*

## Section 3 — Model Answers

### Q1 — Domain Modelling (15 marks) — Sample Solution & Reasoning

**Reasoning walkthrough (this is what should appear in your justification comments, not just the final stubs):**
- `President` is described as "a `Student`" — this is an **is-a** relationship (inheritance or role, not a separate hierarchy branch), but note a student could plausibly stop being president while remaining a student — this is a strong hint `President` is better modelled as a **role reference** (i.e., `Club` holds a `Student president` field) rather than `President extends Student`, since inheritance would wrongly imply presidency is a fixed, permanent type of student.
- `SocialClub` and `SportsClub` share member-management and archiving behaviour, but differ in what kind of activity they organise (`Event` vs `Training`) — shared state/behaviour → **abstract class** `Club`.
- "Archiving behaviour should be available to any club, **and also, separately, to any individual Student**" — two unrelated hierarchy branches (`Club` and `Student`) need the same capability → **interface** `Archivable`, not part of the `Club` abstract class (a `Student` isn't a `Club`).

```java
/** Capability for any entity whose record can be archived while preserving history. */
public interface Archivable {
    void archive();
    boolean isArchived();
}

/** Shared behaviour and state for all club categories. Abstract because SocialClub/SportsClub
 *  share member management and archiving, but differ in what activity they organise. */
public abstract class Club implements Archivable {
    private String name;
    private String description;
    private Student president;                 // association, 1 Club -> 1 Student (president)
    private List<Student> members = new ArrayList<>(); // aggregation: 1 Club -> 0..* Student
                                                          // (a Student can belong to many Clubs, so shared/reassignable)
    private boolean archived = false;

    public Club(String name, String description, Student president) { ... }

    public void addMember(Student s) { ... }
    public void removeMember(Student s) { ... }
    public int getMemberCount() { ... }         // must remain available after archiving

    @Override
    public void archive() { ... }
    @Override
    public boolean isArchived() { ... }
}

public class SocialClub extends Club {
    private List<Event> events = new ArrayList<>();   // composition: Events belong to exactly this club
    public void organiseEvent(Event e) { ... }
}

public class SportsClub extends Club {
    private List<Training> trainings = new ArrayList<>(); // composition
    public void organiseTraining(Training t) { ... }
}

public class Student implements Archivable {
    private String name;
    private String zid;
    private boolean archived = false;

    public Student(String name, String zid) { ... }
    @Override public void archive() { ... }
    @Override public boolean isArchived() { ... }
}

public class Event {
    private String location;
    private LocalDate date;
    // composition: owned entirely by one SocialClub, cardinality 1 (owning club) -> 1..* (events)
}

public class Training {
    private String venue;
    private LocalDate date;
    private int maxParticipants;
    // composition: owned by one SportsClub, cardinality 1 -> 1..*
}
```

**Interface vs. abstract class justification (as required):** `Archivable` is an interface because the capability is needed by two structurally unrelated classes (`Club`'s hierarchy and `Student`), which cannot share a common abstract superclass without an unrelated, artificial merge. `Club` is an abstract class because `SocialClub` and `SportsClub` share substantial real state and behaviour (`members`, `addMember`, `getMemberCount`, `archived`) that would otherwise be duplicated — exactly the `Room` reasoning from Week 3.

**Marking guide:** 3 marks for correctly identifying `Archivable` as an interface with correct justification; 4 marks for `Club` as an abstract class with correct shared fields/methods; 3 marks for correct aggregation vs. composition calls (`Club`–`Student` aggregation, `Club`–`Event`/`Training` composition) with cardinalities stated; 3 marks for `President` not being modelled as `extends Student`; 2 marks for overall Javadoc/clarity of stubs.

### Q3 — Refactoring (13 marks) — Model Solution

**(a) Smells (4 marks — need at least 3 of):**
1. `StudentDiscount` and `SeniorDiscount` duplicate `bookingHistory`, `recordBooking()`, and `summary()` entirely — DRY violation, same as pre-refactor `Room` subclasses.
2. `Discount` is an interface, giving no shared implementation, when substantial state/behaviour is actually shared — wrong choice of abstraction, same as the `Room` interface-vs-abstract-class issue.
3. `DiscountSelector.selectDiscount()` has redundant duplicated `if` conditions (`if (x.equals("STUDENT")) { if (x.equals("STUDENT")) ... }`) — identical structure to the `isDesired()` smell.
4. *(bonus)* `selectDiscount` returns `null` for an unrecognised type with no documented contract for that case — a precondition/postcondition gap (Week 2 connection).

**(b) Refactor (6 marks) — sample:**
```java
public abstract class Discount {
    private List<Booking> bookingHistory = new ArrayList<>();

    public abstract double apply(double price);

    public void recordBooking(Booking b) {
        bookingHistory.add(b);
    }

    public String summary() {
        return "Applied to " + bookingHistory.size() + " bookings";
    }
}

public class StudentDiscount extends Discount {
    @Override
    public double apply(double price) { return price * 0.85; }
}

public class SeniorDiscount extends Discount {
    @Override
    public double apply(double price) { return price * 0.80; }
}

public class DiscountSelector {
    public Discount selectDiscount(String customerType) {
        switch (customerType) {
            case "STUDENT": return new StudentDiscount();
            case "SENIOR": return new SeniorDiscount();
            default: return null;
        }
    }
}
```
*(Marks: 3 for converting `Discount` to an abstract class holding the shared state/methods; 2 for collapsing the redundant `if` nesting in `DiscountSelector`; 1 for keeping `RefactoringRegressionTests`-equivalent behaviour, i.e. `apply/recordBooking/summary` still work identically.)*

**(c) Extension (3 marks) — sample:**
```java
public class FamilyDiscount extends Discount {
    @Override
    public double apply(double price) { return price * 0.80; }
}
```
plus one new `case "FAMILY": return new FamilyDiscount();` in the selector. Justification: because the refactor moved all shared behaviour into the abstract `Discount`, the only code a new discount type needs to write is the one line that's genuinely different (`apply()`'s rate) — exactly the extensibility check from the `BudgetRoom` exercise. *(1 mark for minimal correct code, 2 marks for the justification connecting back to (b).)*

## Section 4 — Model Answers

**Q1 (5 marks).** `ClubManager` demonstrates **abstraction** because its public methods (`createClub`, `addMember`, `getMemberCount`, `listClubs`) describe *what* the system does without revealing *how* clubs/members are stored internally. It demonstrates **encapsulation** because all fields are private, so no external code can corrupt internal state directly. It functions as a **black box** because a caller — including a test — only needs to know the input/output behaviour of these four methods to use the class correctly. A test could verify `addMember`/`getMemberCount` purely through the public interface: call `createClub("Chess")`, call `addMember("Chess", "z1234567")` some number of times, then assert `getMemberCount("Chess")` equals that number — never touching any private list directly. *(2 marks for correctly using all three terms meaningfully, not just naming them; 3 marks for a concrete, correct black-box test description.)*

**Q2 (5 marks).** Returning the internal `List<Club>` directly violates **encapsulation** — it leaks a mutable reference to `ClubManager`'s private internal state to the outside world. Concretely, any caller could now call `.add()`, `.remove()`, or mutate individual `Club` objects on that list, silently corrupting `ClubManager`'s internal state without going through any of its controlled methods (`addMember`, etc.) — the exact failure mode encapsulation exists to prevent (Week 1, section on why public fields are dangerous, generalised to public *references*). A better alternative that still avoids the teammate's duplication concern: keep `listClubs()` returning derived data (e.g. `List<String>` of names, or a read-only/defensive-copy `List<Club>`), computed from the internal list inside the method — this satisfies "don't re-derive names elsewhere" without exposing the mutable internal collection itself. *(2 marks for identifying encapsulation as the violated principle with a concrete consequence, i.e. external mutation of internal state; 3 marks for a correct alternative, e.g. defensive copy or derived read-only view.)*
