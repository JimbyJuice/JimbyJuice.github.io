## 1. Class Design Fundamentals

### Fields
- Always `private` — nobody outside the class touches them directly
- Use `LocalDate` for dates (Java built-in)

### Constructors
- Set the initial state of an object
- Ask yourself: *does it make sense to create this object without this field?*
  - No → require it as a constructor parameter
- `this.field` refers to the field; an unqualified name refers to the parameter

```java
public StaffMember(String name, double salary, LocalDate hireDate) {
    this.name = name;
    this.salary = salary;
    this.hireDate = hireDate;
    this.endDate = null; // current employee — not yet set
}
```

### Getters and Setters — Decision Rule

| Field | Getter? | Setter? | Reason |
|-------|---------|---------|--------|
| `name` | ✅ | ❌ | Name doesn't change |
| `salary` | ✅ | ✅ | Can be updated over time |
| `hireDate` | ✅ | ❌ | Set once at creation |
| `endDate` | ✅ | ✅ | Set when employee leaves |

> **Rule of thumb:** If a field shouldn't change after creation, don't give it a setter. It's easy to add one later if needed; hard to remove one once other code depends on it.

## 2. Inheritance

A subclass **extends** a parent class, inheriting all its fields and methods.

```java
public class Lecturer extends StaffMember {
    private String school;
    private char academicLevel; // A, B, or C

    public Lecturer(String name, double salary, LocalDate hireDate, String school, char level) {
        super(name, salary, hireDate); // MUST be first line — calls parent constructor
        this.school = school;
        this.academicLevel = level;
    }
}
```

### `super` vs `this`

| Keyword | Refers to |
|---------|-----------|
| `this` | The current object |
| `super` | The parent class |
| `this(...)` | Another constructor **in the same class** |
| `super(...)` | The **parent's constructor** — must be first line |

### Key Rules
- A subclass inherits all methods — if `StaffMember` has `getName()`, so does `Lecturer` automatically
- `super(...)` must be the **first line** of a subclass constructor
- You can call a parent's method any time with `super.methodName()`

## 3. Overriding `toString()`

The default `Object.toString()` returns garbage like `StaffMember@1a2b3c`. Override it:

```java
// In StaffMember
@Override
public String toString() {
    return "Name: " + name + ", Salary: $" + salary + ", Hired: " + hireDate;
}

// In Lecturer — reuses parent's version
@Override
public String toString() {
    return super.toString() + ", School: " + school + ", Level: " + academicLevel;
}
```

### `@Override` annotation
- Tells the compiler "I intend to override a parent method"
- If you misspell the method name, the compiler **errors** instead of silently creating a new method
- Always use it when overriding — it's a safety net

## 4. Equality in Java

### `==` vs `.equals()`

| | `==` | `.equals()` |
|-|------|-------------|
| Primitives (`int`, `double`) | Compares values ✅ | N/A |
| Objects (`String`, etc.) | Compares **memory addresses** ❌ | Compares **logical content** ✅ |

```java
String a = new String("Yousha");
String b = new String("Yousha");

a == b        // false — different objects in memory
a.equals(b)   // true  — same content
```

### Overriding `equals()`

```java
// In StaffMember
@Override
public boolean equals(Object obj) {
    if (this == obj) return true;              // same reference → equal
    if (!(obj instanceof StaffMember)) return false;  // wrong type → not equal
    StaffMember other = (StaffMember) obj;
    return this.name.equals(other.name) && this.salary == other.salary;
}

// In Lecturer — reuses parent's check
@Override
public boolean equals(Object obj) {
    if (!super.equals(obj)) return false;      // parent fields must match first
    Lecturer other = (Lecturer) obj;           // safe to cast now
    return this.school.equals(other.school) && this.academicLevel == other.academicLevel;
}
```

### The pattern — 3 steps every `equals()` needs:
1. Same reference check (`this == obj`)
2. Type check (`instanceof`)
3. Cast and compare fields

## 5. Abstract Classes vs Interfaces

### Abstract Classes

- Cannot be instantiated (`new Shape()` won't compile)
- Can have fields, implemented methods, and abstract methods
- Subclasses **must** implement all abstract methods
- A class can only extend **one** abstract class

```java
public abstract class Shape {
    private String colour;

    public Shape(String colour) { this.colour = colour; }

    public String getColour() { return colour; } // regular method — shared code

    public abstract double getArea(); // no implementation — subclass must provide
}
```

### Interfaces

- A **contract** — promises that a class can do certain things
- No fields (constants only), no constructors
- A class can implement **multiple** interfaces

```java
public interface Swimmable {
    void swim(); // no implementation
}

public class Duck extends Bird implements Swimmable, Flyable {
    public void swim() { ... }
    public void fly() { ... }
}
```

### When to use which?

| Situation | Use |
|-----------|-----|
| "A Lecturer **is a** StaffMember" — shared state/code | Abstract class |
| "A Duck **can** swim" — shared capability, unrelated types | Interface |
| Need to inherit from multiple "parents" | Interface (Java only allows one superclass) |

> **Rule of thumb:**
> - Abstract class → **is-a** relationship
> - Interface → **can-do** relationship

## 6. The `static` Keyword

A `static` field/method belongs to the **class**, not any individual instance. All objects share one copy.

```java
public class StaffMember {
    private static int totalStaff = 0; // shared across ALL instances

    public StaffMember(String name, ...) {
        totalStaff++;
    }

    public static int getTotalStaff() { return totalStaff; }
}
```

```java
StaffMember a = new StaffMember("Alice", ...);
StaffMember b = new StaffMember("Bob", ...);

StaffMember.getTotalStaff(); // 2 — called on the CLASS, not an instance
```

### Can you override a static method?

**No.** What looks like overriding is actually **method hiding**:

- Regular methods → Java decides which to call based on **runtime type** (dynamic dispatch)
- Static methods → Java decides based on **declared/compile-time type**

```java
StaffMember s = new Lecturer(...);
s.someStaticMethod(); // calls StaffMember's version — even though s is actually a Lecturer
```

This is why static methods should always be called on the class name (`StaffMember.getTotalStaff()`), not on an instance.

## 7. JavaDoc

JavaDoc is structured comments that generate HTML documentation automatically.

```java
/**
 * Represents a staff member at the university.
 *
 * @author Yousha
 */
public class StaffMember {

    /**
     * Creates a new staff member.
     *
     * @param name      the staff member's full name
     * @param salary    the annual salary in dollars
     * @param hireDate  the date the staff member was hired
     */
    public StaffMember(String name, double salary, LocalDate hireDate) { ... }

    /**
     * Returns the staff member's current salary.
     *
     * @return annual salary in dollars
     */
    public double getSalary() { return salary; }
}
```

### Key tags
| Tag | Purpose |
|-----|---------|
| `@param name description` | Documents a parameter |
| `@return description` | Documents the return value |
| `@author name` | Author of the class |

> **Note:** You only need JavaDoc on **non-overriding** methods and constructors. Don't JavaDoc `toString()` or `equals()` — they're already documented in `Object`.

## Quick Reference — Things That Catch People Out

| Mistake | Why it's wrong |
|---------|---------------|
| `a == b` for Strings | Compares memory addresses, not content |
| Forgetting `super(...)` in subclass constructor | Won't compile, or calls wrong constructor |
| Calling static method on an instance | Works but misleading — use the class name |
| JavaDoc on `@Override` methods | Not needed — already documented in parent |
| Setter for every field | Exposes state that shouldn't change |
| Not calling `super.toString()` in subclass | Loses parent's information in the string |
