## PART 1 — Week 1: Object-Oriented Programming Foundations in Java

### 1.1 A class is a struct with behaviour

**Definition.** A class bundles related data (fields) with the operations that act on that data (methods), into a single unit.

**Intuition.** Your `Average` and `Splitter` exercises don't even use custom classes for their data — they use `int[]` and `String`. But the moment your data has *identity* and *multiple related pieces* (a name, a height, a velocity, a position — see `Satellite`), a plain variable stops being enough. A C `struct` groups fields, but a struct has no behaviour attached to it and no control over who can touch its fields. A Java class solves both problems: it groups the fields **and** it can restrict access to them.

**Why it exists.** As soon as a "thing" in your domain has more than one attribute that must stay consistent with each other, you want a single unit that owns that data and controls how it's read and changed, rather than scattering loose variables around your program.

**Connections.** This is the seed idea that everything else in Week 1 (encapsulation), Week 2 (domain modelling) and Week 3 (abstraction) elaborates on.

**Exam relevance.** MCQ/short-answer questions may ask you to distinguish "class" from "object" (class = blueprint/type, object = a specific instance in memory with its own field values) — this trips people up under time pressure, so be precise.

---

### 1.2 Encapsulation: private fields + controlled access

**Definition.** Encapsulation means hiding an object's internal state behind a public interface (methods), so that the internal representation can change without breaking code that uses the object.

**Why it exists.** If `Satellite`'s `height`, `velocity`, and `position` fields were `public`, any code anywhere could set a satellite's height to a negative number, or bypass any calculation you intended to always run. Encapsulation is what gives a class the power to **guarantee its own consistency**.

**How it works in your Satellite exercise.** Notice the fields are private:

```java
private String name;
private int height;
private double position;
private double velocity;
```

and every single piece of external access goes through a getter or setter. That's not bureaucracy for its own sake — it means that if later you need `setHeight()` to reject negative values, or `getPositionRadians()` to be computed differently, you change it in **one place**, and every caller automatically benefits/is protected. This is the core payoff of encapsulation: *localising change*.

**The design-thinking question to ask yourself:** *"If I make this field public, what invalid states become possible, and who becomes responsible for preventing them?"* If the answer is "nobody," that's a design smell waiting to happen later in the course.

**Bad example (no encapsulation):**
```java
public class Satellite {
    public int height;   // anyone can set height = -500;
}
```

**Improved:**
```java
private int height;
public int getHeight() { return height; }
public void setHeight(int height) { this.height = height; } // could later add validation
```

**Exam relevance.** Design & Programming questions will penalise public fields even if the program "works" — correctness isn't the only thing being marked; encapsulation is graded as part of design quality.

### 1.3 Getters, setters, and the important asymmetry between them

Your `StaffMember` lab spec makes a point that's easy to skim past:

> "Think carefully about what fields should have setters and which shouldn't... If one is not needed, it is better not to add it."

This is a genuinely important design principle, not filler text. Look at the actual `StaffMember` implementation you were given:

```java
// Has both getter AND setter:
public double getSalary()      { ... }
public void setSalary(...)     { ... }
public LocalDate getEndDate()  { ... }
public void setEndDate(...)    { ... }

// Has ONLY a getter — no setter:
public String getName()        { ... }
public LocalDate getHireDate() { ... }
```

**Why this asymmetry is correct design, not an oversight.** A staff member's `name` and `hireDate` are part of their *identity* — they're set once at construction and shouldn't change over the object's lifetime (if the name is genuinely wrong, you'd fix a data-entry error, not "change" it via a legitimate business operation). `salary` and `endDate`, by contrast, are things that **legitimately change during employment** (a raise, a resignation). By omitting setters for `name` and `hireDate`, the class makes those fields effectively immutable after construction — and the compiler now enforces a business rule for you, for free.

**The design-thinking question:** *"Does this field represent something that changes over the object's lifetime, or something fixed at creation? If fixed, why would I give the outside world a way to mutate it?"*

**Common mistake:** Generating a getter+setter pair for every single field reflexively (this is what most IDEs do if you auto-generate). This defeats the purpose of encapsulation — you've just written a public field with extra steps. Only add a setter when there is a genuine reason external code needs to change that value after construction.

### 1.4 Constructors and valid object state

**Definition.** A constructor is special code that runs when an object is instantiated, responsible for putting the object into a valid initial state.

**Why it exists.** The lab spec asks: *"do we ever want to create a staff member without a name?"* — this is really asking you to think about **what counts as an invalid object**. If your class has no-argument constructors or optional fields that leave the object incomplete, you've pushed the responsibility of "remembering to fill in the rest" onto every caller, which is fragile.

**How it works.** `StaffMember`'s single constructor requires `name`, `salary`, `hireDate`, and `endDate` all at once:
```java
public StaffMember(String name, double salary, LocalDate hireDate, LocalDate endDate) {
    this.name = name;
    ...
}
```
There is no way to end up with a `StaffMember` that has `name == null` by accident of forgetting a step — the constructor forces it.

**Connections.** This is your first informal taste of a **precondition** (Week 2's Design by Contract formalises this: "the constructor requires a non-null name" is a precondition on the constructor).

**Exam relevance.** A common Design & Programming task is: "given this requirement, should this be a constructor parameter or a setter call after construction?" Answer using the "is this required for a valid object to exist" test.

### 1.5 Inheritance and code reuse: `extends`, `super()`, and `super.method()`

**Definition.** Inheritance lets a subclass acquire the fields and methods of a superclass, and add or override behaviour.

**Intuition from your lab:** `Lecturer extends StaffMember`. A `Lecturer` *is a* `StaffMember` with two extra fields (`school`, `academicStatus`). Rather than copy-pasting `name`, `salary`, `hireDate`, `endDate` and all their getters/setters into `Lecturer`, `extends` gives you all of that for free.

**The design-thinking question:** *"Is B truly a specialisation of A (is-a), or does B merely use/contain an A (has-a)?"* Get this wrong and you inherit behaviour that doesn't make sense for the subtype (this becomes a formal principle — Liskov Substitution — in later weeks, but the intuition starts here: a `Lecturer` genuinely satisfies everything a `StaffMember` is expected to do).

**Why `super()` matters in the constructor:**
```java
public Lecturer(String name, double salary, LocalDate hireDate, LocalDate endDate,
                 String school, String academicStatus) {
    super(name, salary, hireDate, endDate);   // delegates to StaffMember's constructor
    this.school = school;
    this.academicStatus = academicStatus;
}
```
`StaffMember`'s fields are `private`, so `Lecturer` cannot set `this.name = name` directly even though it inherits the field conceptually — it must ask the superclass constructor to do that job. This is encapsulation and inheritance interacting: **inheritance does not break encapsulation**.

**Why `super.toString()` and calling superclass logic matters — avoiding duplication.** The lab hint explicitly asks: *"You've already written code that does this part in the staff member. Is there any way you can reuse this code without having to copy it?"*

Look at how the given solution answers this for `toString()`:
```java
@Override
public String toString() {
    return super.toString() + ", School: " + this.school + ", AcademicStatus: " + this.academicStatus;
}
```
and for `equals()`:
```java
@Override
public boolean equals(Object obj) {
    if (!(super.equals(obj))) return false;
    Lecturer otherLecturer = (Lecturer) obj;
    return Objects.equals(this.school, otherLecturer.getSchool())
        && Objects.equals(this.academicStatus, otherLecturer.getAcademicStatus());
}
```
**Why this is the *better* design than re-deriving equality from scratch in `Lecturer`:** if `StaffMember` ever adds a new field (say, `employeeId`), `Lecturer.equals()` automatically picks it up because it delegates to `super.equals()` for everything it inherits. If instead `Lecturer` had reimplemented full field-by-field comparison itself, that new field would silently be missing from `Lecturer`'s equality check — a bug caused purely by duplication. This is your first live example of **DRY (Don't Repeat Yourself)**, which becomes a named principle in Week 3.

**Bad alternative (duplicated logic):**
```java
@Override
public boolean equals(Object obj) {
    if (!(obj instanceof Lecturer)) return false;
    Lecturer other = (Lecturer) obj;
    return this.getName().equals(other.getName())      // duplicates StaffMember's logic
        && this.getSalary() == other.getSalary()
        && this.school.equals(other.school)
        && this.academicStatus.equals(other.academicStatus);
}
```
This *works* today, but it's brittle: two independent copies of "what does equality mean" now exist, and they can drift apart.

### 1.6 Overriding `toString()` — the contract, and why it's deliberately open-ended

**Definition.** `toString()` is inherited from `Object`; overriding it lets you control the string representation of your object (used implicitly by `println`, string concatenation, debuggers).

**Intuition.** There's no single "correct" `toString()` — the lab spec says this explicitly: *"No real right or wrong answers for this one."* The design goal is just: **is this useful for a human reading it (in a debugger, in a log, in test output) to understand what object they're looking at?**

**Design-thinking question:** *"If this printed in a stack trace at 3am during an incident, would it tell me enough to diagnose the problem?"* (**Additional clarification** — this framing isn't from your course material, but is a useful mental test.)

**Exam relevance.** Short-answer questions may ask you to justify what you included/excluded from a `toString()`. A reasonable answer references readability and debuggability, not "because the spec said so."

### 1.7 Overriding `equals()` — this one *does* have a strict contract

This is the most exam-relevant Week 1 topic and the one students most often get subtly wrong.

**Definition.** `equals()` defines what it means for two distinct object *references* to be considered logically the same value.

**Why it exists — the pointer-vs-value problem.** The lab hint draws the exact right analogy: in C, `==` on two `char*` compares pointers, not contents — two strings with different addresses but identical characters are `==`-unequal even though you'd consider them "the same string." Java has this exact problem: `==` on objects compares **reference identity** (are these the same object in memory?), never field values. `equals()` is how you define **value equality** on top of reference types.

```java
StaffMember a = new StaffMember("Sam", 90000, date1, null);
StaffMember b = new StaffMember("Sam", 90000, date1, null);
a == b;        // false — different objects in memory
a.equals(b);   // true, once you override equals() to compare fields
```

**How the given implementation works, piece by piece:**
```java
@Override
public boolean equals(Object obj) {
    if (this == obj) return true;                              // (1) short-circuit: same reference
    if (obj == null) return false;                              // (2) never equal to null
    if (!(obj.getClass() == this.getClass())) return false;      // (3) exact type match
    StaffMember other = (StaffMember) obj;                       // (4) safe cast, now that types match
    return Objects.equals(this.name, other.name)
        && this.salary == other.salary
        && Objects.equals(this.hireDate, other.hireDate)
        && Objects.equals(this.endDate, other.endDate);          // (5) compare every field
}
```
- **(1)** is a performance shortcut, not a correctness requirement, but it's idiomatic.
- **(2)** matters because `equals()` must never throw a `NullPointerException` — the `Object.equals` contract requires `x.equals(null)` to return `false`.
- **(3) `getClass() == getClass()` vs `instanceof`** — this is a genuinely subtle and exam-relevant distinction:
  - `obj.getClass() == this.getClass()` requires the objects to be the exact same runtime class.
  - `obj instanceof StaffMember` would also return `true` for a `Lecturer`, because `Lecturer` *is a* `StaffMember`.

  **Why `getClass()` is the right choice here:** it keeps `equals()` **symmetric**. If `StaffMember.equals()` used `instanceof`, then a `StaffMember` could claim to equal a `Lecturer` (since a `Lecturer` passes the `instanceof StaffMember` check) purely by comparing the shared fields — but the `Lecturer` would (correctly) say it does *not* equal that `StaffMember`, because `Lecturer.equals()` requires an actual `Lecturer` on the other side. That breaks the required property `a.equals(b) == b.equals(a)`.
- **(4)** the cast is only safe *because* step (3) already guaranteed the type.
- **(5) `Objects.equals(a, b)` vs `a.equals(b)`:** `Objects.equals` is null-safe — it handles the case where a field is `null` (like `endDate` for a currently-employed staff member) without throwing.

**The formal contract of `equals()` (Additional clarification — standard Java contract, referenced by the Javadoc your lab pointed you to):**
| Property | Meaning |
|---|---|
| Reflexive | `x.equals(x)` is always `true` |
| Symmetric | `x.equals(y)` iff `y.equals(x)` |
| Transitive | if `x.equals(y)` and `y.equals(z)`, then `x.equals(z)` |
| Consistent | repeated calls return the same result if fields haven't changed |
| Null-safety | `x.equals(null)` is `false` |

**Common exam trap:** using `instanceof` in a class that will be subclassed, without realising it can silently break symmetry. If a question gives you a class hierarchy and asks you to write/critique `equals()`, check whether symmetry breaks across the hierarchy.

**Design-thinking question:** *"If I add a subclass to this hierarchy later, does my equals() implementation still behave correctly and symmetrically?"*

## PART 2 — Week 2: Domain Modelling & Design by Contract

### 2.1 From a written spec to a class diagram — a repeatable method

Your Cars UML exercise gives you the actual four-colour methodology used in the course:

1. **Entities/Objects** — nouns that will become classes (`Car`, `Engine`, `Producer`, `Owner`, `Plane`).
2. **Relationships** — how entities connect (`Car` *has* `Engine`(s), `Car` *has* a `Producer`).
3. **Properties/fields/attributes** — nouns that describe an entity but aren't independent things (`speed`, `brand name`, `max speed`).
4. **Actions/functionality** — verbs that become methods (`drive(x, y)`, `fly(x, y, z)`, `travelInTime(dateTime)`).

**Why this ordering works as a method, not just a checklist:** you deliberately separate "is this a class?" from "is this a field?" *before* you start drawing boxes, because the single most common domain-modelling mistake is collapsing something that deserves to be its own class into a mere field (or the reverse — creating a class for something that's really just a property).

**Worked reasoning through your Cars spec:**

- *"Engines are produced by a producer and have a speed."* → `Engine` is a class (it has multiple distinguishing attributes and behaviour like changing max speed), not a `String` field on `Car`.
- *"There are only two [later four] types of engines... Thermal, Electrical, Nuclear, Solar"* → each type has a **different default max speed and different validation rule for what values `setMaxSpeed` will accept** (Thermal: 100–250; Electrical: divisible by 6; Nuclear: prime; Solar: below 150). Different *behaviour*, not just different *data*, for each subtype → this is the signal for **inheritance** rather than a single `Engine` class with an `type` field and `if/else` branches. (You'll formalise *why* the `if/else` version is bad in Week 3 as a code smell — "switching on type.")
- *"A Car has one or more engines"* → an aggregation/composition relationship with cardinality `1..*`, not inheritance — a `Car` **has-a** `Engine`, it is not **is-a** `Engine`.
- *"model the behaviour of Time Travelling for any vehicle"* and *"model flying for any vehicle"* → these are **cross-cutting capabilities** that apply to unrelated branches of a vehicle hierarchy (a `Car` can fly, a `Plane` can fly, but they don't share a common non-`Vehicle` ancestor for "flying"). This is the textbook signal for an **interface** (`Flyable`, `TimeTravelling`) rather than a base class, because Java classes can only extend one superclass but can implement many interfaces — letting a `FlyingCar` be simultaneously a `Car` (extends) and `Flyable` (implements).

**Design-thinking checklist for domain modelling (apply this to any unfamiliar scenario):**
- *"Does this noun have its own identity, attributes, and behaviour, or is it just describing another noun?"* → class vs field.
- *"Do multiple unrelated branches of my hierarchy need this same capability?"* → interface.
- *"Does this specific type always fully satisfy the general type's behaviour, just specialised?"* → abstract class / concrete inheritance.
- *"Is this a 'part of' relationship where the part cannot logically be shared or outlive the whole?"* → composition. *"Can the part be shared or reassigned to a different whole?"* → aggregation.
- *"What are the multiplicities on each end of this relationship?"* → cardinalities (`1`, `0..1`, `1..*`, `*`).

**What NOT to do (from the spec's own warning + course-standard traps):**
- Don't auto-generate the UML from code (the lab explicitly forbids this) — the point is to practise *reasoning from requirements to structure*, which is exactly the skill tested on the exam, where you're never given code to reverse-engineer from.
- Don't model `Owner` as a subclass of anything, or fold `Owner` into `Car` — *"a car has an owner... who can own many cars"* is explicitly a `1..*`-to-`1` (or `*`-to-`1`) association, not inheritance, and not composition (the owner clearly outlives any single car and isn't "made of" cars).
- Don't create separate near-duplicate classes for `TimeTravellingFlyingCar` by copy-pasting fields from `Car`, `Flyable`, and `TimeTravelling` — this is exactly what interfaces + a single concrete class implementing multiple interfaces is designed to prevent.

### 2.2 Composition vs. Aggregation vs. Inheritance — the decision that dominates Week 2

| | Inheritance (is-a) | Composition (has-a, owns) | Aggregation (has-a, shares) |
|---|---|---|---|
| Relationship | Subtype *is* a specialised supertype | Whole *owns* the part; part's lifecycle is tied to the whole | Whole *references* the part; part can exist independently |
| Cars example | `NuclearEngine extends Engine` | `Car` *has* `Engine`s (if engines can't be swapped between cars) | `Car` *has* an `Owner` (the owner exists independently and can own other cars) |
| UML notation | Hollow-triangle arrow | Filled diamond | Hollow diamond |
| When to use A vs B | Use inheritance only when the "is-a" test is unconditionally true for every instance | Use composition when the part has no meaning or independent existence outside the whole | Use aggregation when the part is meaningful on its own and shared/reassignable |
| Common mistake | Using inheritance purely for code reuse when the is-a relationship doesn't actually hold (e.g., making `Square extends Rectangle` breaks when width/height are set independently — **Additional clarification**, classic OOP example, not from your course docs) | Treating every "has-a" as composition by default without checking whether the part can outlive/be shared away from the whole | | 

**Design-thinking question when stuck between inheritance and interfaces:** *"If I removed this behaviour from the class entirely, would the class still make conceptual sense as the same kind of thing?"* If yes, it's a capability that should be bolted on via an interface, not baked into the class hierarchy.

### 2.3 Design by Contract (DbC)

> **Additional clarification:** the exercises you uploaded don't contain explicit DbC material, but you told me this is your Week 2 topic, and it is standard, heavily examined COMP2511 content. Treat the *terminology and structure* below as reliable general software-engineering knowledge, but cross-check exact wording/notation against your own lecture slides before quoting definitions verbatim in an exam.

**Definition.** Design by Contract treats each method as a formal agreement between the caller and the implementer, made of three parts:
- **Precondition** — what must be true *before* the method is called, for the method to guarantee correct behaviour. The caller's responsibility.
- **Postcondition** — what the method guarantees to be true *after* it returns, **given** the precondition held. The implementer's responsibility.
- **Class invariant** — a condition that must hold true for every instance of the class, before and after every public method call (i.e., the object is never left in a state that violates this, from the outside).

**Why it exists.** Without an explicit contract, "correct behaviour" is ambiguous: if a method is called with bad input, is that a bug in the caller, or must the method itself defensively handle every possible input? DbC answers this precisely: **the precondition draws the line.** If the caller violates the precondition, the method is *not* obligated to behave sensibly (this is why unchecked exceptions, covered in Week 3, are often the appropriate response to a precondition violation — it signals a bug in the *caller's* code).

**Connecting this back to Week 1's code, concretely:**
- `StaffMember`'s constructor has an implicit precondition: `name != null`. Nothing in the code enforces this today (there's no `null` check), which is itself worth noticing — a strict DbC approach would either validate the precondition and throw, or explicitly document "behaviour undefined if name is null."
- `StaffMember.equals()`'s postcondition is exactly the formal contract table from section 1.7 (reflexive, symmetric, transitive, consistent, null-safe) — `equals()` is one of the few methods in the JDK where the postcondition is spelled out in exhausting formal detail in the Javadoc, precisely *because* DbC-style contracts matter so much when other library code (like `HashMap`) depends on callers honouring them.
- `Room.book(arrival, departure)`'s postcondition (from the Week 3 material) is explicit in its own Javadoc: *"returns the booking object if the booking succeeded, null if failed."* That's a postcondition described in prose — in a stricter DbC notation you'd write it as: `result != null ⟺ no existing booking overlaps [arrival, departure]`.

**Design-thinking questions for writing contracts:**
- *"What must be true about the arguments for this method to even make sense?"* → precondition.
- *"What do I promise the caller will be true about the return value / object state, assuming they held up their end?"* → postcondition.
- *"What must always be true about this object, no matter what sequence of public method calls got it here?"* → invariant. (For `StaffMember`, a plausible invariant: `endDate` is either `null` or not before `hireDate`.)

**Common misconception:** thinking DbC means "validate everything defensively inside every method." It's closer to the opposite — a strong precondition lets the implementer *skip* defensive checks for conditions the caller has already promised to satisfy, keeping the method's logic simpler. Where you *do* validate defensively (e.g., a public API boundary taking user input) is a deliberate design decision, not the default.

**Exam relevance.** Short-answer questions may give you a method's Javadoc and ask you to state its pre/postconditions explicitly, or give you a buggy method and ask whether the bug is a precondition violation by the caller or a postcondition violation by the implementation — this distinction is exactly what determines whether the fix belongs in the caller or the method itself.

## PART 3 — Week 3: Abstraction, Design Quality, Testing & Exceptions

Your Hotel Booking System lab is the spine of this section — it's explicitly built to teach abstraction, black-box design, and a sequence of code-smell → refactor steps. The Butterflies and archaic_fs exercises add debugging methodology and exceptions.

### 3.1 Abstract Data Types (ADTs) and black-box design

**Definition (from your own lab material):** *"The booking system is broadly speaking an Abstract Data Type — it contains information (data), has meaning (type), and functions as a black box (is abstract)."*

**Why this is "good design"** (this is literally Q1 from your blog, worth answering properly):
- **Abstraction** — `BookingSystemController` exposes *what* you can do (`createHotel`, `addRoom`, `makeBooking`, `hotelJSON`) without exposing *how* it's done (iterating over a `List<Hotel>`, calling into `Hotel`, then `Room`, then `Booking`). A client (test suite, CLI, API layer) only needs to know the public method signatures.
- **Encapsulation** — internal fields like `hotels` in `BookingSystemController` and `rooms`/`bookings` deeper in the hierarchy are all `private`; only accessible through the methods the class chooses to expose.
- **Modularisation** — the system is split into cohesive, separately-responsible classes (`Hotel`, `Room`, `Booking`) rather than one giant class doing everything, so each piece can be understood, tested, and changed in isolation.

**What "black-box" means, and why the tests are black-box (Q2):** A black box is something you can observe the *inputs and outputs* of without needing (or being able) to see the internal mechanism. `BookingSystemTest` only calls public methods on `BookingSystemController` (like `makeBooking(...)` and asserts on its `boolean` return) — it never reaches into `Hotel`'s private `rooms` list or `Room`'s private `bookings` list to check state directly. This means the tests would keep passing even if you completely rewrote the internal implementation (e.g., changed `List<Room>` to a `Map`), **as long as the public behaviour stayed the same** — which is precisely the point of testing through the public interface rather than the internals.

**Design-thinking question:** *"Could I completely swap out this class's internals without touching any of its callers?"* If not, something private is leaking through the public interface (a smell covered later this week).

### 3.2 Reading a method for behaviour and side effects

Your Q3 asks you to characterise `Hotel.makeBooking`:
```java
public boolean makeBooking(LocalDate arrival, LocalDate departure, List<RoomType> preferredRooms) {
    for (Room room : rooms) {
        if (room.isDesired(preferredRooms) && room.book(arrival, departure) != null) {
            return true;
        }
    }
    return false;
}
```
**What it does:** iterates the hotel's rooms in order, and for the *first* room that both (a) matches one of the caller's preferred room types and (b) is free for the requested dates, it books that room and stops.

**Return value:** `boolean` — whether a booking was successfully made anywhere in the hotel. Note this is a **deliberately narrow** return type: the caller can't find out *which* room was booked, or retrieve the `Booking` object, from this method alone. That's a design decision worth noticing (and potentially critiquing) — it's a genuine trade-off between a simple interface and a more informative one.

**Side effects:** this method is not "pure" — calling it *mutates* state deep inside the object graph (a new `Booking` is added to some `Room`'s private `bookings` list as a side effect of the `room.book(...)` call within the loop condition). This matters because:
- Calling `makeBooking` twice with identical arguments does **not** produce the same result the second time (the room may now be taken) — the method is not idempotent.
- Embedding a mutating call (`room.book(...)`) inside a boolean condition (`&&`) is a minor readability smell: a reader skimming the condition for "is this room desired" doesn't expect that same line to also be booking the room. (**Additional clarification** — this observation goes slightly beyond the blog questions but is directly useful design-reading practice for the exam.)

**Design-thinking question for any unfamiliar method:** *"What does the return value tell the caller? What changed in the world (fields, other objects) as a result of calling this, that the return value alone doesn't reveal?"*

### 3.3 Code smell: unnecessary intermediate state (Code A vs. Code B)

```java
// Code A
public void addRoom(RoomType roomType) {
    Room room = null;
    switch (roomType) {
        case STANDARD: room = new StandardRoom(); break;
        ...
    }
    rooms.add(room);
}

// Code B
public void addRoom(RoomType roomType) {
    switch (roomType) {
        case STANDARD: rooms.add(new StandardRoom()); break;
        ...
    }
}
```
**Why Code B is better quality:** Code A introduces a mutable local variable `room` that is initialised to `null` and reassigned inside the switch purely so it can be added to `rooms` once, afterwards. This is unnecessary indirection — it adds a line of code, a moment where `room` is in an invalid (`null`) state, and a (currently harmless, but real) risk: if `roomType` doesn't match any `case` and there's no `default` that assigns `room`, Code A calls `rooms.add(null)` silently, corrupting the `rooms` list with a `null` entry — a bug Code B cannot produce, because it only calls `rooms.add(...)` from inside a matching case.

**The general principle this demonstrates (Additional clarification, but directly the point of the exercise):** prefer performing the action directly at the point where you have the information to do it correctly, rather than staging it through an intermediate variable "for later," when nothing genuinely requires the staging. This is a small-scale instance of a bigger theme you'll meet formally in Week 3/later weeks: minimising the window in which an object is in an incomplete or invalid state.

**Design-thinking question:** *"Does this intermediate variable serve a real purpose (used in multiple places, needs to be returned, needs cleanup logic), or is it just deferring an action I could take immediately?"*

### 3.4 Code smell: switching on type + duplicated conditional logic (`isDesired`)

```java
public boolean isDesired(List<RoomType> preferredRooms) {
    for (RoomType roomType : preferredRooms) {
        if (roomType == RoomType.STANDARD) {
            if (roomType == this.roomType) { return true; }
        }
        if (roomType == RoomType.ENSUITE) {
            if (roomType == this.roomType) { return true; }
        }
        if (roomType == RoomType.PENTHOUSE) {
            if (roomType == this.roomType) { return true; }
        }
    }
    return false;
}
```

**What's wrong with this (Q5), reasoned from first principles rather than pattern-matched:**
1. **Redundant branching.** Every single branch does the exact same thing: check if `roomType == this.roomType`. The outer `if (roomType == RoomType.STANDARD)` etc. contributes nothing — whether `roomType` equals `RoomType.STANDARD` specifically is irrelevant; all that ever mattered was `roomType == this.roomType`.
2. **It doesn't scale.** Adding `BUDGET` later (which the lab does, in Task 5) means adding a fourth near-identical `if` block, copy-pasted, to *every* room subclass's copy of this method (since the smell is repeated across `StandardRoom`, `EnsuiteRoom`, `PenthouseRoom`). That's a change that should require touching one place, requiring four.
3. **The entire method collapses to one line:**
```java
public boolean isDesired(List<RoomType> preferredRooms) {
    return preferredRooms.contains(this.roomType);
}
```
This is not just shorter — it's more *correct-by-construction*: there is no possible way to have a bug where one room type's branch is missing or miscoded, because there are no branches.

**Design-thinking question that generalises this smell:** *"Am I writing a chain of `if`/`switch` branches that all reduce to checking the same underlying condition against different constants?"* If yes, you can almost always collapse it into a single check (as here), or — if the branches genuinely have *different behaviour* per case (not just different constants) — that's the signal for polymorphism / the Strategy pattern (a later-week topic, but the seed is visible right here: **the fix for "switching on type to decide behaviour" is often to let each type know how to answer for itself**, which is exactly what happens in the next refactor).

### 3.5 Code smell: parallel class hierarchy duplicated across interface implementers (Room refactor)

Before refactoring, `StandardRoom`, `EnsuiteRoom`, and `PenthouseRoom` all `implement Room` and each independently re-implement: a constructor that stores its own `roomType`, a `bookings` list, a `book()` method, a `toJSON()` method, and (before 3.4's fix) a copy-pasted `isDesired()`.

**Q6 — code smells present:**
- **Duplicated state and behaviour** across sibling classes (`bookings`, `book()`, `toJSON()` logic re-implemented, or at minimum re-declared, in every room subclass) — a direct DRY violation.
- **An interface being used to force complete reimplementation** of shared behaviour that isn't actually type-specific — `Room` as an `interface` gives *no* code reuse; every implementing class starts from scratch.
- **Only `printWelcomeMessage()`, and later the isDesired constant, is genuinely different per room type** — everything else (bookings management, JSON serialisation, matching preferred types) is identical logic. That's the actual, useful signal: **the amount of behaviour that varies per type is small; the amount that's shared is large.**

**The refactor — why an abstract class instead of an interface (Hint 3):**

| | Interface | Abstract class |
|---|---|---|
| Can hold state (fields like `bookings`, `roomType`) | No (Java interfaces can't hold instance fields) | Yes |
| Can provide a concrete, inherited method body (`book()`, `toJSON()`, `isDesired()`) | No, prior to `default` methods, and even then, no shared *state* to operate on | Yes |
| What subclasses must still supply | Everything | Only what's genuinely type-specific (`printWelcomeMessage()`) |

Because every room needs the *same* `bookings` field and the *same* `book()`/`toJSON()`/`isDesired()` logic operating on it, an **abstract class** (`Room`) can implement all of that once, and declare only `printWelcomeMessage()` as `abstract` — the one piece of genuinely varying behaviour. Each concrete subclass (`StandardRoom`, `EnsuiteRoom`, ...) then shrinks to just a constructor call (`super(RoomType.STANDARD)`) and a one-method override.

**Design-thinking question for interface vs. abstract class (a recurring exam question type):** *"Do the implementing classes share actual reusable state or behaviour, or only a common set of method signatures?"* Shared state/behaviour → abstract class (or an interface with `default` methods, in more advanced designs — but for COMP2511-level reasoning, default to abstract class when state is shared). Purely a common contract with no shared implementation → interface.

**Why this refactor is validated by tests, not just "looking nicer":** the lab explicitly requires `RefactoringRegressionTests` to keep passing throughout. This is the practical meaning of "refactoring": **changing internal structure without changing observable behaviour** — and the only way you can *prove* that, rather than just believe it, is by having a black-box test suite (Part 3.1) that exercises the public interface before and after the change.

### 3.6 Extensibility check: adding `BudgetRoom`

After the refactor, adding a fourth room type (`BudgetRoom`) requires: one new class, extending the abstract `Room`, calling `super(RoomType.BUDGET)`, and overriding `printWelcomeMessage()` — plus one new `case` in `Hotel.addRoom`'s switch. Compare this to how much you'd have needed to touch *before* the refactor (a new `isDesired` copy in the new class, no shared `book()`/`toJSON()` to inherit). **This is the practical test of whether a refactor actually improved the design:** a good design makes the *next* plausible requirement change cheap. (This idea is formalised later in the course as the Open/Closed Principle — you don't need the name yet, but you've already felt the effect.)

### 3.7 Debugging methodology (Butterflies exercise)

**The general process the lab is teaching, independent of the specific bug:**
1. **Reproduce the symptom precisely** — know exactly which assertion fails and what value was expected vs. actual.
2. **Distinguish the symptom from the root cause.** The failing assertion tells you *where the wrongness became observable*, not necessarily *where the logic went wrong* — e.g., a Stage-3 butterfly failing to reproduce correctly might trace back to a growth/stage-advancement method that's off-by-one, several calls upstream of where the assertion checks.
3. **Use the debugger to inspect state at each step**, rather than guessing: set a breakpoint before the suspected method, step through, and watch the actual field values diverge from what you expect at the exact line where they do.
4. **State the fix at the level of the root cause**, not the symptom — "add a special case to make this one test pass" is a red flag; "the growth-stage transition logic doesn't handle Stage 3 correctly" is a root-cause-level fix.

**Design-thinking question that generalises to any bug-hunting exam question:** *"If I only patch the line the assertion complains about, will the same class of bug resurface under slightly different input?"* If yes, you haven't found the root cause yet.

### 3.8 Exceptions: checked vs. unchecked, and where to draw the line (archaic_fs)

**Definitions (Additional clarification of standard Java semantics, applied to your archaic_fs classes):**
- A **checked exception** extends `Exception` (but not `RuntimeException`). The compiler forces every caller to either `catch` it or declare `throws` — Java is telling you "this failure is expected/recoverable, and I refuse to let you forget to handle it."
- An **unchecked exception** extends `RuntimeException`. The compiler does not force any handling — it signals "this indicates a bug in the calling code" (a broken precondition, in Design by Contract terms from Part 2.3).

**Reasoning about `UNSWFileNotFoundException`, `UNSWFileAlreadyExistsException`, `UNSWNoSuchFileException`:** these represent conditions a *well-behaved caller can and should anticipate and recover from* — e.g., trying to `cd` into a path that doesn't exist yet is a completely ordinary, expected outcome when navigating a filesystem interactively, not a programming bug. That's the signature of a condition that should be a **checked** exception: the API is telling every caller "you must have a plan for this outcome, and I won't let you forget it."

**Reasoning about a hypothetical `UNSWNullPointerException`:** Java's own `NullPointerException` extends `RuntimeException`, precisely because a null-pointer dereference is (almost always) a symptom of a **bug** — the caller violated an implicit precondition ("this reference should never have been null here"), not a foreseeable, recoverable business condition. If you created `UNSWNullPointerException`, the design-consistent choice is to make it extend `RuntimeException` (directly, or via extending the real `NullPointerException`) — and consequently, you would **not** need a `try/catch` or `throws` declaration to compile, because unchecked exceptions don't require either. Forcing `try/catch` on every possible null-dereference throughout a codebase would be exactly the kind of "noise for bugs, not business logic" that the checked/unchecked distinction exists to avoid.

**The generalisable design-thinking question:** *"Is this failure a normal, expected outcome of correct calling code (checked), or a symptom that the caller broke a precondition / made a programming error (unchecked)?"*

**Common exam trap:** assuming *all* exceptions related to "files not existing" must be checked just because they sound similar to `FileNotFoundException` in the JDK (which is checked) — the correct reasoning is always from *is this foreseeable and recoverable by a correct caller*, not from surface-level naming similarity.

### 3.9 Testing from a design perspective

**Black-box vs. white-box (tie-back to 3.1):** `BookingSystemTest` is black-box — it tests through `BookingSystemController`'s public methods only. This is only *possible* because the system was abstracted well in the first place; a poorly encapsulated system (fields exposed, logic scattered) would tempt you into white-box tests that reach into internals, which then break every time you refactor even when behaviour is unchanged — directly undermining the value of tests as a safety net during refactoring (as seen in 3.5, where `RefactoringRegressionTests` had to survive a structural rewrite).

**"Test both success and error conditions" (archaic_fs task):** for every operation with a documented exception (e.g., `mkdir` throwing `UNSWFileAlreadyExistsException` when `ignoreIfExists` is `false` and the folder exists), a complete test suite needs both:
- the happy path (folder created successfully), and
- each documented failure path, asserting the *correct exception type* is thrown under the *documented precondition violation*.

This connects directly back to Design by Contract (2.3): a method's contract isn't fully verified until you've tested both "precondition held → postcondition holds" and "precondition violated → the documented failure occurs."

**Coverage (JaCoCo, 80%) as a floor, not a target:** high coverage tells you code *ran* during tests, not that it was *correctly asserted on*. (**Additional clarification** — worth remembering for short-answer questions that ask you to critique a test suite: "100% coverage" is not the same claim as "fully correct.")

### Cross-Week Reasoning Chain (the kind of chain the exam rewards)

> A requirement changes (new room type added)
> → an existing class must be touched in many places to accommodate it
> → that's a sign of **duplicated logic** (Week 3 smell)
> → trace it back to **why** it's duplicated: an interface gave no shared implementation (Week 2's inheritance-vs-interface decision, applied wrongly)
> → refactor to an **abstract class** that owns the shared state and behaviour (Week 3 refactor)
> → verify nothing observable changed by re-running **black-box tests** against the public interface (Week 3 testing, made possible by Week 1/2's encapsulation)
> → the new requirement is now cheap to add, because only the genuinely-varying piece needs new code

### Common Mistakes Across These Weeks

- Reflexively generating a getter *and* setter for every field, ignoring whether the field should be mutable after construction (1.3).
- Using `instanceof` in `equals()` inside a class hierarchy without checking whether it breaks symmetry (1.7).
- Re-deriving `equals()`/`toString()` logic in a subclass from scratch instead of delegating to `super` (1.5) — technically-correct but low design-quality.
- In domain modelling, defaulting every "has-a" relationship to composition without checking whether the part can outlive or be shared away from the whole (2.2).
- Treating Design by Contract as "add defensive null checks everywhere" rather than "state clearly who is responsible for what" (2.3).
- Writing `if/else`/`switch` chains that all reduce to the same underlying comparison, instead of collapsing them (3.4).
- Choosing an interface when subclasses actually need to share real state and behaviour, forcing needless duplication (3.5).
- Treating high test coverage percentage as equivalent to correctness (3.9).
- Assuming an exception should be checked purely because of its name, rather than reasoning from whether the failure is foreseeable/recoverable by a correct caller (3.8).

### High-Yield Knowledge Before Moving to Exam Practice

1. You can write, and justify field-by-field, a correct `equals()` override, including explaining `getClass()` vs `instanceof` and all five contract properties.
2. Given a short scenario, you can decide inheritance vs. interface vs. composition/aggregation, and justify it using "shared state/behaviour" and "is-a vs has-a" reasoning, not vibes.
3. You can state a method's precondition, postcondition, and (if relevant) class invariant from its Javadoc or behaviour.
4. You can look at a method with branching logic and identify whether it's a genuine type-specific difference (→ keep, maybe polymorphism) or a redundant restatement of the same check (→ collapse it).
5. You can explain, in your own words, why testing through a public interface (black-box) is what makes refactoring safe.
6. You can classify an exception as checked or unchecked by reasoning about foreseeability/recoverability, not by name pattern-matching.
