# PART B — SOLUTIONS & MARKING GUIDE

*Attempt Part A fully before reading further.*

## Section 1 — Answers

1. **B.** Almost the entire method body is spent reading another object's data to compute a result — classic Feature Envy.
2. **B.** The precondition narrowed from "any positive factor" to "factor between 0 (exclusive) and 2" — fewer inputs are now accepted, breaking substitutability for callers relying on the wider original contract.
3. **B.** Recursive part-whole nesting (`OrgUnit` containing both `Employee`s and other `OrgUnit`s) with an operation (total headcount) that needs to apply uniformly at any depth — the textbook Composite signal. The others are flat collections with no nesting.
4. **B.** Multiple *combinable* behaviours applied to the same object at runtime — Decorator's signature use case, distinct from Strategy's "one algorithm active at a time."
5. **C.** Decoupling: the subject never needs to change when a new kind of reactor is added, since it only depends on the Observer interface, not concrete reactor classes.
6. **B.** The core Factory Method benefit: adding a new carrier type means adding a new creator subclass, not editing existing branching logic.
7. **B.** Global mutable state + reduced testability, with no benefit gained since the alternative (constructor injection) would achieve the same "one instance in practice" outcome.
8. **A.** `Library` reaches through `member` into `loan` into `book` — a friend-of-a-friend chain that's really asking a question `Member` (or a combination of `Member`/`Loan`) should be able to answer directly.

## Section 2 — Model Answers

**Q1 (3 marks).** Smell: Feature Envy — `PayrollService`'s bonus method is built almost entirely from `Employee`'s data. Violated principle: Tell, Don't Ask (a specialisation of encapsulation). The logic should live on `Employee` (e.g. `employee.calculateBonus()`), because `Employee` owns the fields the calculation depends on, and centralising the formula there means any future change to bonus rules only needs to happen in one place. *(1 mark smell, 1 mark principle, 1 mark correct destination + reasoning.)*

**Q2 (4 marks).** Not LSP-compliant. The base precondition (`stock >= quantity`) accepts any positive `quantity` up to `stock`; the override adds `quantity >= 10`, rejecting inputs (e.g. `sell(3)`) that the base contract accepted. Concrete breakage: code written generically against `Product`, such as `product.sell(1)` in a "buy a single item" checkout flow, works for a plain `Product` but throws/fails for a `ClearanceItem` substituted in its place — violating the guarantee that substituting a subtype shouldn't change correctness. *(2 marks for correctly applying the precondition-narrowing test, 2 marks for a concrete breaking example.)*

**Q3 (3 marks).** This is "friend of a friend": the calling code reaches through `order` to get `customer`, then reaches through `customer` to get `wallet`, then finally asks `wallet` for its balance — three hops of intimacy with objects the caller has no direct relationship with beyond `order`. Fix (call-site only): `double total = order.getCustomer().getWalletBalance();` (assuming `Customer` exposes a `getWalletBalance()` that internally asks its own `wallet` — pushing the last hop inside `Customer`, where it belongs). *(1 mark identifying the chain length/friend-of-a-friend issue, 2 marks for a plausible fixed call site.)*

**Q4 (4 marks).** The loop is testing for **existence of a match** ("does any grade fail?") with early exit — that's `anyMatch`.
```java
boolean hasFailingGrade = grades.stream().anyMatch(g -> g.getMark() < 50);
```
*(2 marks for correctly naming `anyMatch` with the "existence + short-circuit" reasoning before writing code, 2 marks for correct implementation.)*

**Q5 (4 marks).** Strategy: an interface representing *one interchangeable algorithm*, exactly one of which is active/selected at a time for a given operation (e.g. one comparator used to sort). Decorator: an interface whose implementations can be *layered/composed together*, with multiple decorators active simultaneously around the same base object. Scenario where confusing them breaks the design: needing to combine gift-wrapping **and** express shipping on the same `Order` — if this were modelled as Strategy (one algorithm swapped in for "how to process the order"), you could only pick *one* of gift-wrapping or express shipping, not both, without creating a combined `GiftWrappedExpressStrategy` class per combination — exactly the combinatorial explosion Decorator avoids. *(1 mark per pattern's one-sentence distinction, 2 marks for a concrete scenario showing the wrong choice failing.)*

**Q6 (4 marks).** Testability: any test exercising a class that internally calls `SessionManager.getInstance()` is implicitly coupled to whatever global session state exists at test time, making it hard to test with a controlled/fake session without extra machinery to reset or substitute the singleton between tests. Coupling/global state: 40 classes now depend on a single, mutable, globally-reachable point — any of them can change session state in a way the other 39 don't expect, and the dependency is invisible from each class's constructor/interface (you can't tell what a class depends on just by reading its public API). Alternative: pass a `Session` (or `SessionManager`) instance into each class's constructor explicitly (dependency injection) — still only one instance is created in production, but tests can substitute their own instance, and the dependency is visible in each class's signature. *(2 marks each problem, correctly distinguished; no extra credit for restating one problem twice.)*

## Section 3 — Model Answers

### Q1 — Domain Modelling (15 marks) — Sample Solution & Reasoning

**Reasoning walkthrough:**
- "each item is either an individual `Track`, or another `Playlist`... arbitrarily nested... same operation regardless of depth" — this is a direct restatement of Composite's defining scenario: a `PlaylistItem` interface (Component), `Track` as `Leaf`, `Playlist` as `Composite`, with `getDuration()` defined on the interface and implemented recursively on `Playlist`.
- "`Artist` should not need to know anything concrete about what kind of notification each subscriber wants... more channels expected later without modifying `Artist`'s code" — this is a direct restatement of Observer's defining scenario: `Artist` is the Subject, `NotificationChannel` (or similar) is the Observer interface, concrete channel classes (`EmailNotifier`, `PushNotifier`, ...) implement it without `Artist` ever referencing them by name.

```java
/** Component of the Composite pattern: any item that can appear inside a Playlist. */
public interface PlaylistItem {
    int getDurationSeconds();
}

public class Track implements PlaylistItem {   // Leaf
    private String title;
    private int durationSeconds;
    private Artist artist;                      // association: 1 Track -> 1 Artist

    public Track(String title, int durationSeconds, Artist artist) { ... }

    @Override
    public int getDurationSeconds() {
        return durationSeconds;
    }
}

public class Playlist implements PlaylistItem {  // Composite
    private String name;
    private List<PlaylistItem> items = new ArrayList<>();
    // composition: items belong to this playlist's ordered sequence; cardinality 1 -> 0..*
    // (a Track/Playlist appearing in one Playlist's sequence is owned by that sequence position;
    //  note: if the same Track is intentionally shared across multiple Playlists' *catalogues*,
    //  that specific relationship would be aggregation instead — justify per your own reading)

    public void addItem(PlaylistItem item) { items.add(item); }

    @Override
    public int getDurationSeconds() {
        int total = 0;
        for (PlaylistItem item : items) {
            total += item.getDurationSeconds();   // recursive delegation — works at any nesting depth
        }
        return total;
    }
}

/** Observer interface: any channel capable of notifying a user of a new release. */
public interface NotificationChannel {
    void notifyNewTrack(User user, Track track);
}

public class EmailNotificationChannel implements NotificationChannel {
    @Override
    public void notifyNewTrack(User user, Track track) { ... }
}
// PushNotificationChannel, InAppNotificationChannel implement the same interface similarly

public class Artist {                            // Subject
    private String name;
    private List<User> subscribers = new ArrayList<>();  // aggregation: Users exist independently, 1 Artist -> 0..* subscribed User
    private List<NotificationChannel> notificationChannels = new ArrayList<>();
    // (each subscribed User's preferred channel(s) could alternatively be modelled per-User;
    //  either structure is acceptable as long as Artist depends only on the interface)

    public void subscribe(User user) { subscribers.add(user); }

    public void releaseTrack(Track track) {
        for (User subscriber : subscribers) {
            for (NotificationChannel channel : notificationChannels) {
                channel.notifyNewTrack(subscriber, track);
            }
        }
    }
}

public class User {
    private String name;
    // ...
}
```

**Marking guide:** 4 marks for `PlaylistItem`/`Track`/`Playlist` correctly structured as Component/Leaf/Composite, including a correct recursive `getDurationSeconds()` body; 2 marks for explicitly naming Composite in the justification comment; 4 marks for `NotificationChannel` as an Observer interface with at least two independent concrete implementations, and `Artist` depending only on the interface (not concrete channel classes); 2 marks for explicitly naming Observer in the justification comment; 3 marks for correct cardinalities/relationship types on `Playlist`–`PlaylistItem` and `Artist`–`User` with justification.

### Q2 — Programming From Scratch (12 marks) — Key Design Points to Self-Check

- `Beverage` is an interface with `cost()`/`description()`, implemented directly by `Espresso` (2 marks).
- `Milk`/`ExtraShot` implement `Beverage` **and** hold a wrapped `Beverage` field, set via constructor (3 marks — this is the core Decorator structural requirement; a decorator that doesn't hold a wrapped `Beverage` reference isn't a decorator).
- `cost()` in each decorator returns `wrapped.cost() + <own addition>`, not a hard-coded total — this must delegate, not duplicate (3 marks).
- `description()` similarly appends to the wrapped description rather than replacing it (2 marks).
- The `main` method constructs something like `new ExtraShot(new Milk(new Espresso()))` — nesting decorators around each other, not a special-cased combined class (2 marks). Full marks require that swapping the order or adding a third decorator would work without any new class — if your code has a `MilkAndExtraShotEspresso` class anywhere, that's the exact smell this question is testing you against.

### Q3 — Refactoring (13 marks) — Model Solution

**(a) Smells (5 marks — 3 required, matching the hinted categories):**
1. **Feature Envy / Law of Demeter** in `Library.hasOverdueLoans` and `Library.calculateLateFee` — both reach into `member.getLoans()` and interrogate individual `Loan` objects directly, duplicating the same overdue-checking logic in two places. This logic is more naturally `Member`'s (or `Loan`'s) responsibility.
2. **LSP violation** in `GuestMember.canBorrow()` — the base `Member.canBorrow()` has an implicit precondition-free contract "true if fewer than 5 active loans"; `GuestMember` tightens this to "fewer than 1," meaning code written generically against `Member` that assumes the 5-loan ceiling (e.g. code that lets a member borrow a 2nd book because `canBorrow()` was checked and often returns `true` under that assumption) can behave surprisingly for a substituted `GuestMember`. *(Note: strictly, `canBorrow()` returning a stricter `true/false` isn't a precondition on an argument the way `sell(quantity)` was in Section 2 Q2 — the discussion here is about the **postcondition/contract** `Member.canBorrow()` establishes being narrowed in a way that could surprise generic callers; full marks accepted for identifying this as an LSP-relevant behavioural narrowing even if the pre/post framing is looser than a parameterised method.)*
3. **Missing Strategy** in `calculateLateFee`'s `if (type == STANDARD) ... else if (type == PREMIUM) ...` branch — an `if`/`switch` picking between fee-calculation algorithms by type, which will need editing every time a new member type is added.
4. *(bonus)* `printLoanCount` also has a Law-of-Demeter-flavoured chain (`mostRecentLoan.getMember().getLoans().size()`), reaching through `Loan` into `Member`'s internals from a method whose name suggests it should just be asking `Member` directly.

**(b) Refactor (5 marks) — sample:**
```java
// On Loan:
public boolean isOverdue() {
    return !returned && dueDate.isBefore(LocalDate.now());
}

public long daysOverdue() {
    return isOverdue() ? ChronoUnit.DAYS.between(dueDate, LocalDate.now()) : 0;
}

// On Member:
public boolean hasOverdueLoans() {
    return loans.stream().anyMatch(Loan::isOverdue);
}

// Library becomes a thin caller:
public boolean hasOverdueLoans(Member member) {
    return member.hasOverdueLoans();
}
```
*(Marks: 2 for moving the overdue check onto `Loan` as `isOverdue()`, 2 for `Member` exposing a direct query rather than `Library` iterating `member.getLoans()` itself, 1 for `Library`'s methods becoming simple delegating calls with identical observable behaviour.)*

**(c) Strategy refactor (3 marks) — sample:**
```java
public interface LateFeeStrategy {
    double calculateFee(long daysLate);
}

public class StandardFeeStrategy implements LateFeeStrategy {
    public double calculateFee(long daysLate) { return daysLate * 0.50; }
}

public class PremiumFeeStrategy implements LateFeeStrategy {
    public double calculateFee(long daysLate) { return daysLate * 0.20; }
}
// Member holds/exposes its own LateFeeStrategy (e.g. set at construction based on type),
// so Library.calculateLateFee sums daysOverdue() * member.getLateFeeStrategy().calculateFee(...)
// without ever branching on MemberType itself.
```
Justification: adding `StaffMember` now means writing one new `LateFeeStrategy` implementation; `Library`'s fee-calculation code never needs to change, because it only depends on the `LateFeeStrategy` interface, not on which concrete member types exist — exactly the extensibility payoff demonstrated with `Comparator` in this document's Strategy section. *(2 marks correct structure, 1 mark justification connecting to extensibility.)*

## Section 4 — Model Answers

**Q1 (5 marks).** Problem 1 (Singleton cost): 15 classes depending on `NotificationCentre.getInstance()` directly means the dependency is invisible from each class's own interface, and testing any of them requires dealing with global singleton state — the same testability/coupling cost as Section 2 Q6. Problem 2 (triggering mechanism): each caller independently branching on notification kind duplicates dispatch logic 15 times, and adding a new notification-worthy event, or a new channel, means touching many call sites. Combined fix: keep (or replace) `NotificationCentre` as an explicitly-passed dependency rather than a global singleton, and restructure the triggering side using **Observer** — the classes that currently call `NotificationCentre` directly should instead be Subjects that notify registered `NotificationChannel` observers, removing the need for each of the 15 call sites to know about or branch on notification kinds itself. *(2 marks per problem correctly distinguished, 1 mark for a combined fix naming Observer specifically.)*

**Q2 (5 marks).** "There's only one in our system" describes a fact about the current deployment, not a requirement that the *type system* must enforce it — apply the design-thinking question: does anything break if two `Library` instances technically could exist, or does the program just happen to only construct one? If nothing depends on the enforcement itself (no code relies on `Library` refusing to be instantiated twice), Singleton buys no real benefit here beyond convenience, at the cost of global state and testability (Section 2 Q6). Alternative: construct one `Library` instance at program start-up (e.g. in `main`, or a composition-root/setup class) and pass that single instance into every class that needs it via its constructor — this achieves the same "exactly one instance exists in the running program" outcome without a global static accessor, and tests can construct their own independent `Library` instance freely. *(2 marks for correctly challenging the justification using the design-thinking question, 3 marks for a concrete, correct alternative with the "no static accessor, testable" reasoning.)*
